## Summary

Today the execute session's messages are **copied** into the chat session (terminal echoes, routing reaction rows, interaction cards, failure receipts), which turns the chat into a joint transcript of two sessions: six write sites, eight idempotency-key prefix conventions, best-effort writes whose failure means "lies forever", and a frontend that infers state from the *absence* of a row. ADR-100 spent Rev.2 through Rev.8 patching that mirror.

This ADR removes the mirror itself, in three moves:

1. **Introduce `round` as the single cross-model primary key** — minted deterministically by the Runtime at the turn boundary, durable, stamped on the metadata of every entry the round produces in the execution session. It does not exist in the code today.
2. **The chat stores no copies of execute messages, only one `execution_round` reference row** (no body). Block content is **projected at read time** from the execution session, and the projection lands in a **disposable side table owned by acowork-user** (same shape as ADR-097): pulled on first render, persisted, served locally afterwards.
3. **chat → execute delivery becomes an explicit addressing ladder**: `@` carries two levels of meaning (agent addressing, then session selection); no `@` means chitchat by default; the LLM may only **propose** a target, never deliver silently.

Net effect: cross-process durable writes drop from six classes to one, and the exec → chat direction has **zero writes**. The chance of a lie moves from "a network call failed" to "a local index can be rebuilt".

## Background (all verified against the code)

### 1. The mirror is the only source of the write-back complexity

A turn's obligations toward the chat are spread over six write sites today: `post_intent_response` (router answering itself; the terminal state of a chat-routed turn), `echo_terminal_row` (three sites in [session_task.rs](../../../core/acowork-runtime/src/agent/session/session_task.rs): attachment parse failure / turn end including `aborted` / loop `Err`), `write_interaction_card` + `close_chat_card` ([loop_interaction.rs](../../../core/acowork-runtime/src/agent/loop_interaction.rs)), the `turn_routed` reaction row (two sites: [chat_router/runner.rs](../../../core/acowork-runtime/src/agent/chat_router/runner.rs) and [gateway_loop.rs](../../../core/acowork-runtime/src/startup/gateway_loop.rs)), `router_fallback`, plus Gateway-side `delivery_failed`, the §6.5 R4 receipt and the sweeper's `fallback-` timeout rows. Idempotency keys are an informal string-prefix convention (`exec:` / `tr:` / `rf:` / `card:` / `ir:` / `resp-` / `dlv-failed:` / `fallback-`) with no type-level constraint.

The consequence is not "complexity", it is **lying**: every one of these writes is best-effort (failure only `warn`s), while the pending-row predicate in [chatTurnState.ts](../../../apps/acowork-desktop/src/components/chat/chatTurnState.ts) is exactly "the latest human row has no terminal answer". A failed terminal write means that round stays "in progress" in the chat forever.

### 2. The reason for the mirror was already removed

"Making the chat context more complete" was the only motive for copying — the router needed to see what was happening in the execution sessions in order to route. Once the router no longer holds the power to *guess an old session and deliver silently* (Decision 6), it needs none of the execute content: chitchat reads only the chat's own rows, and dispatch reads only candidate metadata ([chat_candidates.rs](../../../core/acowork-runtime/src/agent/session/chat_candidates.rs) already reads metadata only, per ADR-096). **The consumer of the mirror is gone.**

### 3. The Rev.4–7 pin retrospective: projection repays Rev.8's cost for free

Rev.4 moved the execution view's composer to the chat entry precisely so that *the human's own sentence typed against an execution session would appear in the chat transcript*; Rev.6 and Rev.7 kept patching the pin; Rev.8 finally cancelled the requirement and recorded the price honestly: "the chat transcript cannot show that question; the round leaves only an interaction card and a standalone echo in the chat".

Under references + projection that price is repaid automatically: the block renders the execution session's own transcript, **both sides of the exchange coming from the single source of truth** — no proxied write, no exception to the identity model, no pin.

### 4. D1's real boundary is narrower than its wording

ADR-100 D1 deleted `ExecSessionStatusCard` — projecting the execution session's **state machine** (busy / idle / which step) into the chat transcript *and treating it as a durable fact*. Volatile state and an immutable log can never line up; that conclusion of D1 stands.

This ADR projects the execution session's **durable transcript slice** (one round's user message + reply). There are not two truths, because there is only one copy and it is a cache, not a source of truth. D1 therefore needs restating precisely as: **no second *durable* truth; never project the execution session's *state machine* as a fact.** The block's "in progress" appearance is derived by the positive-evidence rule of Decision 9, not by polling a state machine.

### 5. Group and direct chats are the same predicament projected twice

Group: `@agent` addresses explicitly; without `@`, ADR-105's `default_responder` is needed as a fallback. Direct: one agent, but N execution sessions, so an unspecified input has to be guessed by an LLM. Both lack the same thing — **an addressing model with an explicit fallback semantic**. Today the group uses `mentions` + `auto_routed_to` and the direct chat uses the router's `dispatch(existing)`: two mechanisms doing one job.

### 6. Two foundational facts verified

- **The `round` key does not exist.** `round_id` has zero hits repo-wide (one unrelated test name only); execution storage is the flat `append_message(role, content, metadata)` stream of [conversation.rs](../../../core/acowork-runtime/src/conversation.rs), paginated by ADR-050 **physical entry offsets**, with no notion of a round. → Decision 2 is the first piece of work.
- **Cross-machine reads already work.** The Runtime publishes a retained `acowork/agents/{id}/http_endpoint` whose value is `{node proxy base}/agents/{id}` ([agent_init.rs](../../../core/acowork-runtime/src/startup/agent_init.rs), re-published on network change per §6.3.3); `proxy_to_runtime` builds the target URL straight from it and attaches `X-ACowork-Node-Token` ([proxy.rs](../../../core/acowork-gateway/src/http/proxy.rs)). `GET /sessions/{sid}/messages` reads through the UseCase layer's file access and **does not require the session to be Active** — an ADR-038 `Closed` session (on disk, not resident) is readable, consistent with Rev.7. So as long as **the Runtime process is up**, the transcript of any session on any node is readable. Process down → `agent_not_running` / `503` → which is exactly why Decision 5's cache must exist.

## Decisions

### Decision 1 — The chat's kind vocabulary converges to four, with four invariants

| kind | producer | carries |
| --- | --- | --- |
| `user_message` | the human, written by the Gateway under the token identity | the **only** input of a chat |
| `agent_message` | the chat session itself (chitchat / triage answer) | output ①: conversation |
| `execution_round` | the Runtime, when it hands a round of work to an execution session | output ②: a **reference**, no body |
| `system_notice` | channel facts (`delivery_failed` / `budget_exhausted` / `truncated` / `unavailable`) | unrelated to exec |

`interaction_request` / `interaction_resolved` **leave the chat vocabulary** (Decision 8). The legacy `text` and the `intent_request` / `intent_response` normalisation stay.

- **I1 (single container)** — a chat stores only its own utterances plus references to work.
- **I2 (two identities)** — anything the chat knows about exec exists either as a durable **reference fact** (carrying no content) or as a volatile **projection cache** (disposable, rebuildable). Neither is a second source of truth.
- **I3 (addressing first)** — delivery authority follows: explicit addressing > propose-and-confirm > chitchat by default. The LLM has no silent delivery right.
- **I4 (one key)** — one round = one `round_id`, the only join key across the two models, minted deterministically by the Runtime at the turn boundary, never inferred from ordering.

### Decision 2 — `round_id`: minted deterministically by the Runtime at the turn boundary, durable, never inferred

- **Minting point**: **the execution session's turn boundary**, exactly one place — entry and exit of `AgentLoop::run` ([loop_.rs](../../../core/acowork-runtime/src/agent/loop_.rs)), through which every turn shape passes (chat delivery, the execution-surface composer, intent and PM dispatch). The Gateway entry does not mint it.
- **Shape**: `round_id = "r:{inbound_message_id}"` — a deterministic derivation of the round's inbound message id; opaque string, ≤ 128 bytes. That id already exists for every turn-creating entry (chat delivery carries the chat message id; the composer carries the frontend-generated `msg-{uuid}`; an intent carries the protocol's message_id). **An id that is too long, or whose character set cannot be addressed, is hash-folded** to `r:{digest}-{len}`: the string goes straight into a URL path, a file name inside the conversations directory and a SQL bind, so the character set the next hop accepts and the one the upstream can produce must be **the same predicate** (`is_addressable`) — otherwise a round is born unreadable; and the fold must stay a deterministic function of unbounded input, or a re-delivery would mint two rounds.
- **The fold's digest must be a stable digest** (SHA-256, first 8 bytes as implemented), not a standard-library hasher whose algorithm is an implementation detail: this string is not an in-memory key. It is written into every row of the round, into Decision 4's side table, and from P4 on it is the reference row's idempotency key `round:{round_id}` — an identity that has to stay stable forever. A toolchain upgrade that changed the digest would mint a second round for a message that was already delivered (a duplicate block, a duplicate run), and nothing could detect it.
- **Why a deterministic derivation rather than a UUID minted at the entry** (this clause is a correction made while validating the implementation): ① **no protocol change** — no new field on proto `Intent`, no lockstep release of Gateway and Runtime; ② **it preserves the existing re-delivery dedup** — MQTT re-delivering the same `message_id` is deduplicated by exactly that id today (`exec:{message_id}`), and a random UUID would throw that property away; ③ uniqueness is guaranteed by whoever generates the message id, which is the same guarantee a UUID would give.
- **Persistence**: **every** entry the round produces (user / assistant / tool / attachment) carries the same `round_id` in its metadata. The injection point is the write funnel `append_message_with_id` ([conversation.rs](../../../core/acowork-runtime/src/conversation.rs)) — all JSONL writes go through it, so no call site has to thread a parameter and none can be forgotten. The Decision 4 round index is upserted at the same time.
- **Answering a card does not mint**: when the previous turn ended `waiting` (a `pause` card still open) this turn **continues** the active round — the predicate is "the previous turn's outcome was `waiting`, or the session still holds an unclosed `pause` card" together with an unclosed active round. After a process restart the active-round state is gone ⇒ the turn degrades into a new round, which self-heals (Decision 4's crash repair closes the stale record), so no permanent "in progress" is left behind.
- **No inbound id and no parked round means no round at all** (a clause added when the mint was implemented): `mint_round_id("")` falls back to a random UUID, and a random id names a round nobody can re-address and no chat reference row can ever point at — writing it would produce a phantom block. So such a turn runs **unstamped** instead: its rows stay durable in the transcript, they simply belong to no round index and project to no block. Every transport supplies an inbound id, which makes this a degenerate branch rather than a fallback, and `TurnSurface::new` and `run` enforce the same predicate so nobody mints an id outside the turn boundary.
- **Ordering inference is forbidden**, on four counter-examples: context compaction (ADR-010/032/061 rewrite the representation of what came in), forced pre-emption opening a new round (pending queue), DevMode resume/step **replaying the same round** (ADR-013 — `replay` opens no round, and replayed entries still land under the original `round_id` stamp), and the idempotent re-post of `append_message_with_id` (same id ⇒ same `round_id`; the index folds to the last record per id, so a re-delivery simply overwrites). Any one of them breaks "adjacent messages are the same round".
- **A replay shares the turn boundary** (the landing point of the third counter-example): `AgentLoop::replay` uses the same open/close pair as `run`. Replaying rows with no stamp freezes that round's `answer` coordinate on the row written before the pause — and that round has usually already reached terminal, so it gets cached: the real answer produced by resume would then never appear in the chat, with nothing to heal it. The round id comes first from the active round the writer still holds (a continued round is not named after this message id), then from the message id, and only if neither exists do these rows carry no round.
- **`TurnSurface` shrinks** accordingly to `{ chat_session_id, round_id, answerable_by, has_human }`. The ADR-100 Rev.6 patch (the runtime back-filling the chat coordinate from the session binding) stays; `trigger_message_id` disappears **from the surface**, because the reference row is itself the anchor and the presentation layer never needs to point back at a triggering row. **Correction made while implementing P4**: the fact itself did not leave the system — Decision 3's row shape always required `in_reply_to`, so the trigger id is now supplied by `TurnReference` (alongside `opened_new` / `assignment_brief`). What retired is the mirror writes' use of it as an idempotency key and a thread pointer, not the fact.

### Decision 3 — `execution_round` is the chat's only durable unit of work

```json
{ "kind": "execution_round",
  "in_reply_to": "<the user_message id that triggered it>",
  "meta": { "round_id": "…", "agent_session_id": "…", "agent_instance_id": "…",
            "opened_new": true, "assignment_brief": "… (optional, only for new)" } }
```

- **No `body`**: a reference row carries no execution content. The task name shown by the presentation layer comes from the Decision 4 projection (plus the session title).
- **The idempotency key is the natural key**: `meta.message_id = "round:{round_id}"`. Uniqueness is guaranteed by the minter, so a re-delivery deduplicates by construction. **The prefix-key family convention (`exec:` / `tr:` / `card:` / `resp-`) retires entirely, leaving this single rule.**
- **Consistency classes become explicit**: the reference row is **prepositive** (delivery is only allowed after the write succeeded; on failure the human message returns to undelivered, and no "delivered but invisible" round is created). Channel receipts and human message rows are prepositive too. There is no third class in the exec → chat direction, because there is no write in that direction any more.
- **`turn_routed` retires**: the conversational fact it recorded ("your message went to a session / new task vs continuation") is expressed by the reference row itself (a reference row exists = the message went somewhere; `opened_new` = new or continued). Rev.3's motive for restoring that row ("a chat must have turns") is satisfied by the block presentation of Decision 9, which is more honest than an empty-body notice.
- **The writer is the Runtime**, through the Gateway's single chat write entry. No second write entry, and the ADR-009 §5 filesystem redline stays intact (`run_gateway_fs_redline` in `dev/ci.sh` remains green).
- **The one write site is the round boundary inside `AgentLoop::run`, not a transport** (confirmed by the implementation, and the exact shape of "six sites collapse into one"): the reference row has to be written under the `round_id` this round is about to use, and Decision 2's card-continuation rule makes that id **not a function of this turn's inbound message** — only the turn boundary knows which round it is opening, so a transport-side write would necessarily name the wrong round on the continuation branch. Transports therefore supply facts (`TurnReference{trigger_message_id, opened_new, assignment_brief}`) and write nothing. `append_chat_row` has exactly one call site in the whole Runtime crate, which is the checkable form of "the write sites went from six to one".
- **A failed precondition opens nothing**: when the reference row cannot be written, or the execution session has no `session_id` of its own (the row's shape requires `agent_session_id`, and a reference no reader can resolve should not exist), the turn returns `Err` before its first token is spent — no round is minted and no user row is appended. "Delivered but invisible" is unconstructable at this layer.

### Decision 4 — Read-time projection: the Runtime owns the computation "what a round is"

- **New endpoint**: `GET /sessions/{sid}/rounds/{round_id}` (Runtime loopback, Gateway-proxied), returning the **conversation-visible projection** of that round: `{ user: {body, attachments, ts}, answer: {body, status, ts}, card: {kind, request_id, prompt, options} | null, terminal: bool }`.
- **"What a round is" is defined by the execution session, not by the chat** — this is the core of the boundary. Tool calls, thinking and streaming do not enter the projection (ADR-100 D3's "execution details never enter the chat" becomes "never enter the projection": same semantic, now stricter — they don't need to be persisted at all).
- **A round derived index is mandatory**, otherwise this endpoint scans the JSONL on the request path and violates the ADR-096 redline (`run_session_full_read_redline`).
- **Index location**: `{conversations_dir}/{session_id}.jsonl.rounds` — the session's own append-only side table, sibling of the JSONL main store, **the same shape as ADR-097's disposable side table** (fold on read, first-touch rebuild, corruption means rebuild). The name is a suffix on the transcript's own name and must not be `{session_id}.rounds.jsonl`: inside the conversations directory the `.jsonl` extension **is session identity** (the conversation index enumerates sessions by extension and reconciles them by `{sid}.jsonl`), so that name would be swept forever as a session whose lines never parse, and could never be reconciled away. Not a SQLite table: a session holds tens to hundreds of round records, a JSONL side table gets "disposable" with zero new dependencies, and the writer of it is already the JSONL's single writer thread (ADR-092) — no second writer and no cross-crate schema dependency.
- **Record shape**: `{ round_id, user, answer?, card?, terminal, status?, ts }`. `user` / `answer` are **ADR-050 data-index coordinates**, noted by the write funnel as it commits those lines (O(1)), so a projection reads exactly two lines plus one **bounded small window** after the user row (to fold attachment entries) — never a full scan.
- **Maintained by the single writer**: the writer switches rounds when an entry's `metadata.round_id` differs from the active one; a record with `terminal=true` **is never rewritten afterwards** — the property the cache's whole design (Decision 5) rests on.
- **A coordinate counts only while the row itself vouches for it**: the Decision 5 cache has **no invalidation path**, so a stale coordinate served as content would be frozen permanently as "what this block says". The projection therefore checks the two rows it fetched: right role, and the row's own `metadata.round_id` equal to the round asked for. A missing transcript, an out-of-range coordinate and a coordinate that lands on another round's row are all an **explicit hole** (404 on the single read, `found: false` on the batch) — never someone else's message, and never a 500 (only a genuine read failure returns `Err`, so a caller can still tell a retryable outage apart from a permanent hole).
- **A bounded window must be vouched for too**: a window is a *range*, and a range is the one thing this projection may not trust — a round cut off before it answered (crash, interrupt) has no `answer` coordinate to close the window, so the window would run on into the next round. Rows inside it therefore also need their own stamp to equal the round asked for, or they do not belong to this block. On the writer's path an attachment row goes through the same funnel as the user row (`append_message_with_id`) and already carries the stamp, so this check costs no real attachment.
- **The read path rebuilds too**: "first touch" must not mean only the writer opening the session. When the side table is empty (lost, or never produced) and the transcript exists, the read rebuilds it from the transcript, persists the records and then projects — otherwise a session whose side table was cleaned up would answer holes forever while every fact it needs is still in the transcript. Where records already exist, it does **not** rebuild (a rebuild would bypass the `card` a terminal snapshot carries and the cache layer accepts).
- **Crash repair**: when a session loads, any record still marked `terminal=false` gets a closing `terminal=true, status="interrupted"` record appended. "In progress" therefore cannot stay stuck because the process was killed — the property ADR-100 D10's absence-based inference lacked.
- **An open round**: `terminal=false`. The projection is read from disk only (the side table's latest snapshot plus the flushed transcript lines), **never from in-memory state** — which is why an active round is still readable when the session is not resident and after a process restart, at the price that it is only current as of the last flush. The client MUST NOT cache it, and that is enforced by the cache layer refusing the write itself (Decision 5) rather than by the orchestrator remembering to filter.

### Decision 5 — The projection cache lives in acowork-user, is orchestrated by the Gateway, and is built as a disposable side table per ADR-097

- **Storage**: `{data_dir}/chat-sessions/{sid}/rounds.sqlite`, one per chat, sibling of and modelled on `search.sqlite` (ADR-097). Keyed by `(agent_instance_id, agent_session_id, round_id)`, value = the Decision 4 projection + `fetched_at` + `terminal`. **A terminal round is immutable ⇒ there is no invalidation problem**: that is the property making this whole cache design sound, and why there is no TTL, no version number and no change notification.
- **Why acowork-user, and not the Gateway or the frontend**: ① lifecycle — deleting a chat must take this copy of execution content with it (privacy), and directory-level cleanup is only free on the same side as the chat store (ADR-084 puts chat storage in acowork-user); ② a frontend cache violates "the Desktop app is presentation only, with no state persistence"; ③ the Gateway owns no transcript data, and hosting one there invites filesystem overreach. **This copy is a derived artefact of the chat, in the same family as `lines.index` and `search.sqlite`.**
- **Who fetches**: the Gateway. It is the only process that can reach every Runtime (`proxy_to_runtime` + the node reverse proxy + the node token). acowork-user must not call a Runtime in reverse — its `/internal/*` surface only accepts writes from the Gateway.
- **Read path**: `GET /api/chat-blocks/{chat_id}?refs=…` — a **new top-level prefix**; it cannot hang under `/api/chat-sessions/*`, because that prefix is wholesale forwarded to acowork-user by [user_proxy.rs](../../../core/acowork-gateway/src/http/user_proxy.rs) and the route is already owned. Flow: batch-look-up the side table for the requested refs (`GET /internal/chat-sessions/{id}/rounds`) → serve anything hit and `terminal` → for the rest, **group the refs by `(agent_instance_id, agent_session_id)` and make one batched `?ids=` request per execution session** (≤ 64 ids per upstream request, ≤ 200 refs per render, more than that is a 422) → write back only the `terminal=true` projections via `PUT /internal/chat-sessions/{id}/rounds` → answer **in request order**, each ref in one of four states: `ok` / `pending` / `not_found` / `unreachable`. A ref is **never silently dropped** — dropping one lets the frontend invent a row for it. `X-Error-Origin` semantics follow ADR-055 §6.17.
- **Two guards on refs**: refs arrive from the client, so ① **shape validation** — the triple `instance|session|r:round`, each segment restricted to `[A-Za-z0-9_.-]`, with no leading `.` and no `:` in a session or instance id, because those values go straight into a URL path, a query string and a SQL bind; ② **the binding guard** — the Runtime stamps every projection with the execution session's own `chat_session_id` (read off the session meta, never from a request header), and the Gateway serves and caches only projections **bound to the chat being read**, turning anything else into `not_found` plus a `warn`. Without the second guard, a member of two chats could pour the other chat's execution content into this chat's cache and have it survive as history.
- **Three predicates, one set — and this layer may only be narrower**: the minting predicate (`is_addressable`), the cache key predicate (`rounds_cache::valid_id`) and the Gateway's segment check must be the same character set, and all three must refuse `..`. A token waved through here but rejected downstream fails **the whole batch** there (a cache read answers a single bad token with a 422 over the page), and the Gateway reads any non-2xx as "cache unreadable ⇒ every ref missed" — so one bad token would permanently disable the cache for that page and make every render pay a full cross-host refetch. That is Decision 9's "one broken ref must not contaminate" violated from the other direction.
- **Shape validation does not contaminate**: a token that fails ① does **not** reject the request with a 422; it is answered in its own response slot as `not_found`, with the token echoed back. A 422 would let one broken transcript row make every *other* block in the page unreadable, while silently dropping the token would let the surface invent a row for it — Decision 9's "never silently drop" cuts both ways. The 422 is reserved for genuine request-level errors: nothing asked for, and more than `MAX_REFS`. Same rule on the Runtime side: a malformed `round_id` in a batch read answers `found: false` (the single read still 400s, because there is only one answer there).
- **A retryable fault must not masquerade as a permanent hole**: the batch read records "this round exists but its rows could not be read" on that item as `found: false` **plus** `error`, and the Gateway must map that item to `unreachable` (with a retry affordance), not to `not_found`. The difference between the two is exactly Decision 9's first invariant: rendering a disk hiccup as "this round never happened" leaves the surface with no reason to retry, and Decision 5's cache has no invalidation path to rescue it.
- **Disposable and self-healing** (ADR-097 D3/D4 adopted clause by clause): a cache write failure only `warn`s and never affects the response; a corrupt / missing / lying side table degrades to "re-fetch" and never taints chat reads or writes; byte and row caps with LRU eviction; **ordering contract**: release the handle before `remove_dir_all` (on Windows a SQLite file without `FILE_SHARE_DELETE` turns "a disposable side table" into "a chat that cannot be deleted"), and the cache read and write must happen **inside** the per-chat `session_lock` — the same lock `delete_session` takes — because `connect()` does `create_dir_all(parent)`, so an open landing outside the lock resurrects a chat mid-deletion and strands a live handle behind it. That is not only a stuck delete: it is a privacy leak, a copy of execution content outliving the chat it came from.
- **Degradation shape**: Runtime unreachable (`agent_not_running` / `session_not_ready` / node offline) and no cached copy → the block renders "work record temporarily unreachable (node offline / session deleted)", with the last known state and a retry affordance. That is an **explicit, readable hole**, not a lie. With a cache hit the history stays fully readable offline — which is where the "no remote RTT on first paint" promise is kept.
- **What is never cached**: open rounds — and that is enforced by the cache layer itself (the write entry `warn`s and skips any row marked `terminal=false`), not by the orchestrator remembering to filter; a cached row that is `terminal=false` or whose payload is not an object is distrusted and treated as a miss, because the correct response to a lying row in a disposable cache is "ask again", never "believe the side table"; and anything beyond the block's own content (tools / thinking are outside the projection, so they are outside the cache too).

### Decision 6 — An addressing ladder replaces the router's single guess; the LLM loses silent delivery

Priority high → low, first match wins:

| level | trigger | behaviour | LLM |
| --- | --- | --- | --- |
| 1 | `in_reply_to` points at an `execution_round` (the human replied to that block) | deterministic continuation into that session's next round | none |
| 2 | `@agent` + a named session (second `@` level) | deliver to the named session | none |
| 3 | `@agent`, exactly one deliverable session for that agent in this chat | deliver directly; several → a session-picker card | none |
| 4 | group, no `@` → `default_responder` (ADR-105 D1–D3 retained) | enters that agent's chat session, continue at level 5 | — |
| 5 | no `@` (direct chat, or after the fallback) | **chitchat by default**; `exec_session_create(brief)` only on a clear new-task intent; `exec_session_propose_continue` **plus a confirmation card** when it looks like a continuation | proposal only |
| 6 | PM `task-dispatch` | machine-form explicit addressing (the `conv:task` key) | none |

(**Revision (2026-11-04)**: level 2 of this table no longer delivers — a typed `@` on a session now yields reference material, and the message falls through the rest of the ladder as usual (a message carrying refs also skips level 3's continuation branch); continuation moves to the block's inline input box, hitting level 1; answering level 3's choice card still delivers through `target_sessions` — that address is one the human chose, not one typed. See the revision section at the end of this document.)

- **Level 1 is the correct answer for the highest-frequency continuity case**: "the agent just reported progress and I reply to it" needs no LLM guess — replying to the block *is* the addressing act. That empties most of level 5's guessing workload, so the cost of a confirmation is never spread over every message.
- **Level 5's confirmation must have a cheap escape**: propose only when the deliverable candidate set (Decision 7) is non-empty; otherwise silently take `exec_session_create` or chitchat. "Start a new task" is always the sibling option on the confirmation card, escapable in one click.
- **Answering an addressing card is not a new utterance** (added at P6): a `session_choice` / `confirm_continue` card asks "where should the sentence you just wrote go?", so the answer is **the same text re-delivered with the address just chosen**, carrying the original row's `message_id`; the chat store dedupes on that id, so the transcript still holds one message — writing a fresh row would show the human the same sentence twice. The address is also given only to **the agent that asked** (the same rule as Decision 7's `force_new_for`). A card leaves once answered: "answered" is decided by a reference row existing for the message it asked about (Decision 3), and hitting that stops it being rendered at all (the same exit as D14 — the block's own rounds and status already say what was decided, and a receipt line would state the same fact a second time). So "it is gone on click" is not a disappearance but a **handover**: the card yields the slot to the execution block under the same avatar and name.
- **A card must be answerable, or it must not exist** (**Rev. 2026-11-06**): an addressing card's `in_reply_to` has to name **a row this chat actually holds**, and that row has exactly one derivation — "which Chat row does this delivery answer?": for a group `@` fan-out it is the shared `user_message` row id (the envelope's `in_reply_to`), for a 1:1 message it is the envelope's `message_id`. The Runtime's `chat_row_id` is the single implementation of that derivation, shared by all three writers (the reference row, the level-3 choice card, the level-5 confirmation card); the per-target delivery uuid must **never** be a card's subject — it names nothing in the chat, so `GET …/answer` can only answer `origin_gone` (422) and the card can never be answered and never leaves. The rule lands in two places: the write entry (`acowork-user`'s `append_message`) refuses a card whose subject is absent from the log — answerability is what a card **is**, not an option; the read side (`chat_view`) reports such a card, already on disk from an older build, as `answerable: false`, and the surface renders none of it (the same exit as "answered", D14: a question that cannot be asked is no more a conversation record than an answered one). The log is append-only, so old rows are not migrated. **The card's durability stays**: a question has to be there after a page reload, which is exactly why it cannot be live-only information — what had to be fixed is the durability of *dead* questions, not the durability of questions.
- **Who may answer is a presentation-layer permission, not a property of the row** (Decision 10's third tier): the card is handed only to the person named by `meta.to`; in local mode (no account system, so no id to compare) exactly one person is speaking, and refusing there would hide the only answerable card in the app.
- **The silent `dispatch(target=existing)` right is deleted**, and with it Block C's `S1..S10` alias table (addressing moves from "the LLM cites an alias" to "a human names it"). The router's act space: `answer` / `exec_session_create(brief)` / `exec_session_propose_continue(session, why)` / `ask_human(question)` (act names renamed by the 2026-11-04 revision — the old `new_task` / `propose_existing` are recorded at the end of this ADR; the same revision adds the read-only `exec_session_read_round`, which brings the alias table back for that tool alone).
- **`route_intent_legacy`'s `routing_key` guess chain** (`conv:task` > `chat:{csid}:{initiator}` > `conv` > `msg`) keeps only the `task:` branch and "named by a reference row / `@`"; the `chat:csid:initiator` "go back to the last session by default" branch is deleted — it is the high-error class.
- ADR-099's layering (D1), stateless router + per-chat queue (D2), candidate isolation (D4), three-block context orchestration (D5), strict chat/execute prompt separation (D6) and failure degradation (D8) **all stand**; degradation no longer needs a machine-assembled chat excerpt, because the default target at level 5 is chitchat, not some session.

### Decision 7 — Two levels of `@`: agent addressing, then session selection

- **Level 1 (agent)**: candidates are the chat's agent participants. A direct chat has exactly one agent ⇒ this level degenerates and the UI skips it, going straight to level 2. This is where "group and direct chat share one logic" lands: **a direct chat is the special case of a group with agent count = 1**.
- **Level 2 (session)**: (**Revision (2026-11-04): the selected session no longer receives a delivery — it becomes reference material (`meta.refs`); the permission set, the candidate read and paging-as-window are all unchanged**, see the revision section at the end of this document.) candidate set = **permission** (reusing [chat_candidates.rs](../../../core/acowork-runtime/src/agent/session/chat_candidates.rs) unchanged: 1:1 lists sessions bound to this chat plus sessions the human started by hand; a group lists only sessions *I* initiated; kinds never mix; a session an agent started carries an instance UUID as its `initiator`, which never equals a human account id, so agent↔agent runs never reach a human's list). `Errored` is kept ("you should go back and look" is a useful signal); **no display predicate is layered on top of the permission set** — a `Closed` (non-resident) session is still addressable and the dispatcher reopens it, so residency drops no rows; the only exclusion is a session whose PM task already reached a terminal state (reviving a finished chain is not a legal continuation target).
- **`@` selects a destination, it does not create a binding**: session ownership is still decided by the single truth of Decision 11; "the seed only applies on creation" is unchanged, and because naming no longer depends on a mapping table the "seed silently ignored" branch disappears.
- **The addressable set may only come from the Runtime, and it gets no endpoint of its own** (added at P6, amended since): `GET /api/agents/{id}/sessions?chat_session_id=&surface=` (a transparent Gateway proxy → the session listing the Runtime already had). "Which execution sessions may I address inside this chat" and "this agent's session list" are the same question asked twice, and a second endpoint only produces two answers that can drift apart — `/chat-candidates` was deleted for that reason. The candidate filter IS the permission, and the permission lives on the node that owns the execution sessions; letting the picker recompute it would offer sessions the router would have refused. Two walls stand: chat membership (a non-participant gets the same 404 as a chat that does not exist) plus the initiator's visible set — and that "I" comes from the Gateway-injected `x-user-id`, never from a query parameter, because otherwise anybody could name somebody else's visible set. **The filter runs BEFORE pagination** ⇒ `total_count` / `total_pages` count only legal rows, so **the paging is the window**: the 20-row cap and the 7-day freshness test are gone with the endpoint and a human may page back as far as they like; a session they never page to is still in the transcript, reached by replying to its block, not by failing to deliver.
- **Both levels use one entry point** (`POST /api/intents/mentions`, `targets` plus the new `target_sessions` and `force_new_for`); the client no longer forks on "with @ / without @" — ADR-105 removed the first fork, this removes the second. `force_new_for` is **a list, not a flag**: a fan-out delivers one utterance to several agents and the human can only refuse continuation for the one they were answering, so a flag would let `@A @B` with "new task" picked for A silently start a new session for B too. Validation is explicit: an id in the address must be among this message's `targets`, and the same id must not appear in both `target_sessions` and `force_new_for` (a server must not guess between contradictory instructions).

### Decision 8 — Interaction cards move into the block; answers go straight to the execution session

- `ask_user_question` / permission approval **no longer write an `interaction_request` row into the chat**. A card is an execution-side fact about "what this round is waiting for"; the Decision 4 projection surfaces it as the `card` field and it renders inside the block.
- **Answering uses the execution session's own write entry** (`POST /api/agents/{id}/sessions/{sid}/…`, with ADR-076 §Decision 4 second-wave identity checks), and the Gateway additionally verifies the caller is the round's `answerable_by` (the initiator) and a participant of the chat. `resolve_card_answer`, `mark_answered`, the end-of-turn safety net and `chatTurnState.closedCards` all retire.
- **The two kinds of card are not one mechanism** (added at P6): an execution-side interaction card (`ask_user_question` / approval) lives inside the block, and answering it writes the execution session (this Decision); an addressing card (`session_choice` / `confirm_continue`) is a question inside the chat, and answering it re-delivers (Decision 6). The first leaves no chat row; the second never touches the execution session.
- **The change in group visibility was argued to be no worse than today** (Decision 10): D9's echo already surfaced that round's output to the whole group; under the new model participants still see the block and its card (read), and only the initiator can answer (write).
- **`has_human == Some(false)`** (agent↔agent) needs no "skip writing the card" special case any more — nothing is written to the chat at all.

### Decision 9 — "In progress" is a presentation state, proven by positive evidence

- The single durable predicate for a block showing "in progress": an `execution_round` reference row exists **and** the **live** projection for that `round_id` (`source=runtime`) reports `terminal=false`. A cached `terminal=false` cannot exist (Decision 5's forced refusal), so "in progress" can never be sourced from a stale side-table snapshot.
- **Unreachable is not in progress**: when the Runtime cannot be consulted and nothing is cached, that ref is answered `unreachable` (with a retry affordance) and renders "temporarily unreachable", never "still running" — showing an outage as in progress lets a stopped node rewrite what happened.
- This is **positive evidence** (a reference row exists ⇒ a round is running), not ADR-100 D10's negative evidence ("no terminal row ⇒ still running"). The absence-derived pending row (`opensAgentTurn` reading three kinds of evidence — `to` / `auto_routed_to` / `mentions` — plus `answeredAfter` closing on `delivery_failed`) retires wholesale. **What that pending row should take as its positive evidence** is restated in the Revision (2026-11-03) at the end of this document — the same kind of evidence, with the credential extended from an in-flight POST to this device's own send claim.
- **Streaming text and tool progress remain presentation-only**: they reuse the existing `session_state` / chunk MQTT push (ADR-036/049/035), subscribed only for sessions behind blocks in the viewport, and they **never enter storage, never enter context building, never enter unread counts**. D1's constraint bites here precisely: no reading the state machine to *assert* a historical fact.
- An empty-body terminal still renders as a centred status row (`aborted` / `failed` / `timeout` / `waiting`) — `terminal.status` comes from the projection, so no chat row is needed for it. Rev.3's avatar invariant is retained.

### Decision 10 — Three permission layers; chat membership is the authorization basis for block content

| what you want to see | authorization basis | enforced at |
| --- | --- | --- |
| the existence of a reference row | chat participant | acowork-user (the existing `not_a_participant`) |
| block content (the projection) | **a participant of this chat** (the new layer added here) | Gateway `GET /api/chat-blocks/*`: verify participation first, fetch from the Runtime with the service credential, re-verify before serving |
| pressing a button inside a block | the round's `answerable_by` (initiator, ADR-076) | the execution session's existing owner check on its write entry |

- The execution session's own `authorize_read` stays owner-only. Block projection is **not** a loosening of exec read rights; it is one authorized read on the chat data plane: the Gateway fetches with the node token (a machine credential, ADR-055 Phase 5a) and then decides, from chat membership, whether to serve it. That the session is bound to the chat (the single truth of Decision 11) is the precondition for this layer to exist at all.
- A group member who is not the initiator sees content (read) but not control (write). This equals today's behaviour (D9's echo rows were already visible group-wide), so it is not a privacy loosening.
- A `user_user` 1:1 chat with no agent never produces a block.

### Decision 11 — One truth for the binding: retire `intent-sessions.json`

- The only durable truth of a chat binding is **the execution session's meta `chat_session_id`** (ADR-100 D9 already used it as the basis for "a session permanently belongs to a chat"); "which sessions does this chat have" is answered by a derived index over session metadata, reading metadata only (ADR-096).
- `IntentSessionMap` (`intent-sessions.json`) in [intent_routing.rs](../../../core/acowork-runtime/src/agent/session/intent_routing.rs) retires, taking with it the double-write of "re-point the mapping + stamp" inside `chat_dispatch(Target::Existing)` and the ownership question of the `TerminalSessions` mirror. Three coexisting truths (mapping file / session meta / the Gateway mailbox's `source_chat_session_id`) collapse to one meta plus one derived index; the mailbox field is a **delivery fact**, not a binding fact, and stays.
- **May one execution session be referenced by several chats?** No. The binding stays unique, so block ownership and `@` permissions do not re-complicate. Reaching work from another chat uses the "view execution" jump, not a copied reference. This is an explicit scope boundary, not an oversight.

### Decision 12 — agent↔agent and PM dispatch collapse into the same reference

- An agent↔agent intent no longer writes `agent_message` request/response rows into the chat (the `resp-` family); it writes **one `execution_round` reference row on the chat the target session is bound to** — it always was a round of work. `ensure_pair(agent_agent)` stays (the pair chat remains the transcript container) but stops carrying content.
- **Rev. 2026-11-06**: a PM `task-dispatch` **does write one `user_message` row**, and the reference row lands under it (`in_reply_to` = that row's `message_id`) — isomorphic to a 1:1 send: one human input plus the execution session it opened, **persisted as a pair** and **entering the chat session's context as a pair** (`chat_history_read` and the Chat Router's Block B read that row as `[user:<created_by>] …`; the reference row carries no body and does not enter the context, exactly as in a 1:1 pair — which is how a chat session can read the thread of who asked whom to do what). The earlier wording — "that message lives in the execution session and is naturally visible through the projection" — held only for **body visibility**: it made the reference row's `in_reply_to` name a mailbox id (`pm-…`) instead of a chat row, so the block had no trigger, the transcript held no sentence (unread, in-chat search and the list preview all saw nothing), and the only place the task survived was a projection used as a naming fallback — the same dangling-coordinate defect as a card written under a per-target delivery uuid. The row's voice is `Task::created_by`: a human-filed task is spoken by the human, a PM-created one by the PM agent; the body is only `build_dispatch_message` (task title + description), while the wake-up playbook stays on the envelope's `assignment_brief` and touches no chat surface (Decision 13 rev., design 27 §5.4.5). Task-key routing stays (Decision 6, level 6).
- "Who writes to the chat" therefore has exactly two producers: **the Gateway (human `user_message`)** and **the Runtime (`execution_round` / `agent_message` / `system_notice`)** — and the exec → chat direction has no producer at all.

### Decision 13 — Re-assigning search, previews, unread counts and titles

- **List preview / optimistic title**: the reference row's `assignment_brief` (or a one-line summary of the first round, produced once by the Runtime when writing the reference row and never rewritten) is enough. **Rev. 2026-11-06**: that string must come from the human-readable dispatch text (`acowork-pm`'s `build_dispatch_message`) and **never** from the envelope's identically named high-trust `assignment_brief` — the latter is the wake-up playbook, which `acowork-pm` documents as "never persisted, never displayed on a chat surface". The Runtime read the two same-named facts as one, so the playbook became a durable row name and surfaced in the project group's list preview and round line. Rendering a list must never read the projection (ADR-096). **Rev. 2026-11-08**: that prohibition targets list shapes that would prefetch a projection for every row (the sidebar session list, the optimistic title). The in-conversation history dialog is user-initiated, reads only the rows it currently has loaded, and folds them into one projection read per page — so it is not the prohibition's object. It writes nothing to `search.sqlite` and copies no execution body into any other cache.
- **Global search / in-chat search** (ADR-097 / ADR-081): `search.sqlite` indexes the chat's own rows plus each reference row's `assignment_brief` (**Rev. 2026-11-08**: a reference row has no body, so `assignment_brief` is its only searchable text — which is why it is a **full-text column** of `search.sqlite`, not merely a stored one; stored-but-unindexed would leave the very line the user can see in the history list unfindable by search); **it does not index the projection cache** — that would feed one disposable copy into another disposable index, turn deletion into a two-hop problem, and exec content is already searchable through the conversation index (ADR-082 / ADR-095). Cross-session body search goes to the exec index, hits "a round of a session", and the jump path already exists ("view execution").
- **Unread**: counts the chat's own rows only. A block's "waiting for a human" state is a separate badge (from `card != null` in the projection) and never mixes into unread counts.

### Decision 15 — Three hard rules of the write contract (Rev. 2026-11-06)

The first two turn "a question and its execution, as a pair" from a **convention** into a **type**; the third stops the coordinate from being guessed. All three live at the single write entry ([chat_sessions.rs](../../../core/acowork-user/src/chat_sessions.rs)'s `append_message` and [chat_turn.rs](../../../core/acowork-gateway/src/intent/chat_turn.rs)'s `open`), never as a read-side fallback — a read-side fallback only lets "this row points at a sentence nobody wrote" keep displaying as fact.

- **A coordinate must resolve.** Any row carrying a non-empty `in_reply_to` must name a row that is **already in this session's log**; empty means an **origin row** (this round was not asked by a sentence in this chat: an agent↔agent request, a cron wake, an assignment its author opened), which is legal and is the fact. Three measured defects had exactly this shape, and each one cost a human-visible hole: a card naming a group `@` fan-out's **per-target delivery uuid** (a question that could never be answered — `…/answer` returned 422 `origin_gone` forever), a block naming a PM mailbox id `pm-…`, a limit receipt naming a peer request id. A producer either writes the row it points at first, or declares itself an origin.
- **A dispatch speaks as its author.** A `task-dispatch` is a chat sentence before it is a round of execution: the row's voice is `Task::created_by` — a human-filed task is spoken by the human (`user_message`), a task an agent created is spoken by that agent (`agent_message` + `meta.task_id`, i.e. an **assignment**: no sentence in this chat asked for that work, so it needs **no** `in_reply_to`, which is what Decision 12's earlier text was reaching for with "origin"). A dispatch therefore requires its author to be a participant of the group; an author with no voice cannot dispatch (the Gateway returns `chat_log_unavailable` and PM records the reason on the task and retries on its existing backoff) — put the other way, **letting someone file a task in a project is letting them speak in the project's chat**, and the two judgements must agree. The judgement therefore sits at **creation**: a non-member is read-only in a project, so `POST /projects/:id/tasks` and the MCP face return 403 `author_not_project_member` (`acowork-pm`'s `ensure_author_has_voice`, the same roster as `ensure_assignee_is_member` — owner or member), leaving dispatch's `chat_log_unavailable` as a backstop for paths that bypass creation rather than as the normal expression of a permission.
- **The producer declares the coordinate; the receiver does not derive it.** A delivery carries `chat_row_id` on the envelope (`Intent.chat_row_id` in `mqtt_payload.proto`), which is the id of the row the Gateway just wrote; the Runtime takes it as given instead of deriving it from `message_id` / `in_reply_to` — that derivation guessed wrong in both shapes that matter (a group fan-out's per-target uuid, a mailbox id), and it is the shared mechanism behind the three defects above.

## Presentation contract (the block is the conversation-scale sibling of an explore block)

An explore block in the execution view folds one run of "tool calls + thinking"; a block in the chat folds **one execution session's** worth of "questions + replies + whatever card a round is waiting on". The grammar is copied from the explore block; the only invention is what a row pairs — `user` / `assistant` instead of `tool_call` / `tool_result`.

**Storage is per round, rendering is per session** (the presentation face of Decisions 3 and 4): one execution session appears in the transcript exactly once, as one block; the trigger rows it folds (the human messages named by a reference row's `in_reply_to`) stop standing on their own as bubbles — one sentence shows up in one place, and Decision 6's re-delivery is the precedent for that rule. **Revision (2026-11-04)**: the round that opened a new session (a reference row whose `meta.opened_new` is true) is a fork of this folding rule — its trigger row stays a bubble of its own; see the revision at the end of this ADR.

- **Anchor**: the session's **newest** reference row inside the loaded window. A long-lived session advancing across days pulls its block down with it instead of staying where it first appeared — that is how "a session is a rendering target, not a storage unit" lands. Two sessions in one window stay two blocks, ordered by their own anchors.
- **Header**: agent avatar + name (a block always starts a new turn, so it wears the avatar/name a bubble wears) + run name (session title first, else the first round's triggering body truncated — ADR-100 D8's task-name resolution moves verbatim into the presentation layer) + `N rounds · status` + the task id (Decision 13: a label, never a link).
- **Status**: the execution session's `session_state` where it is known (awaiting the model / streaming / running a tool / waiting for approval / paused…), falling back to the newest round's terminal projection copy. v1 streams nothing, so the header carries no per-token update; "is it still running" stays a Decision 9 `pending` read, and `session_state` only refines the wording.
- **Expanded**: the last **2** rounds by default, the rest behind a "show N earlier rounds" control inside the block; only the newest round opens its own question/answer pair, earlier rounds collapse to one line — this is what keeps a block from stretching the transcript a screen taller.
- **One row per round**: the row leads with the round number and a status glyph (in progress = pulsing dot / done = check / failed = red cross / interrupted = amber cross) and shows the question as its summary; opening it reveals the question panel and the answer panel, copying the explore block's "arguments panel / result panel" two-layer grammar. What cannot be read is said as unreadable (unreachable with a retry, `not_found` as an explicit hole) rather than drawn as an empty box (Decision 5).
- **Jump**: "view execution" is its own control ABOVE the block — the block opens the execution session as an object, not one of the rows listed inside it; rounds no longer carry a repeated jump.
- **Cards**: the decision a round is parked on renders at BLOCK level and stays answerable while the block is folded (Decision 8); in a group chat a viewer who is not the round's answerer sees the question plus why the buttons are gone (Decision 10's read/write split).
- **`@` addressing**: both the 1:1 and the group composer carry `@`. The group's first level picks an agent / a member, the 1:1's is degenerate (one agent) and its second level picks the task as before — an address is an instruction a human gives, never something a model may re-decide (Decision 7).
- Mobile: same grammar and the same class structure; the delta is presentation density only — the newest round's answer stays inline, a card collapses to one line and its buttons live in the bottom sheet (§6.5). `session_state` covers only the foreground watched session, so a block paints a live line only when its own session is the watched one.

## Rejected alternatives

| Alternative | Why rejected |
| --- | --- |
| Continue the hygiene work (a typed `ChatWrite`, unified idempotency keys, best-effort writes moved into an outbox with retry) | It treats symptoms: the root cause is six write sites becoming one. An outbox still has to handle the whole class of "cross-process write into storage that is not yours" |
| One reference row **per execution session** instead of per round | The timeline would lie: a session advancing across days would leave its block parked at its first appearance. "A session as a whole" is a **rendering** goal (group by session), not a **storage** unit (store per round) |
| Redundantly storing a final-answer excerpt in the reference row (a "light mirror") | Straight back to mirroring: an excerpt must be updated, an update is a cross-process write, a failed write is a lie. The list preview is satisfied by the one-shot `assignment_brief`, which never needs updating and never claims to be the transcript |
| The cache in the Gateway's own data directory | Deletion decouples from the chat lifecycle (a privacy residue), and it tempts the Gateway into owning transcript data. ADR-084 already assigns the chat data plane to acowork-user |
| The cache in the frontend (IndexedDB / localStorage) | Violates "the Desktop app is presentation only, no state persistence", and every surface would keep its own copy |
| No cache: fetch remotely on every render | N blocks on first paint = N cross-machine RTTs; a Runtime restart turns every block into a hole; offline and weak networks become unreadable |
| The round index storing the answer body instead of only the coordinates | Not taken: the side table stores `data_index` coordinates and the body comes from the JSONL main store. A redundant body is one more disposable copy, and since a projection reads two lines there is no performance case for it; worse, it would turn ADR-096's "derived at write time" into a second writable source of content |
| Letting the LLM judge continuity and silently deliver to an old session | That is the origin of the Rev.4–7 pin saga and of "one extra empty execution session per message". A high-error choice must be revocable, i.e. confirmed |
| A dedicated new live channel for the projection | `session_state` / chunk pushes already exist; adding a channel would create the second live truth D1 was written to kill |

## Impact

- **Data**: exec side gains `round_id` metadata plus the rebuildable `{sid}.jsonl.rounds` side table (**it dies with the session**: `delete_session` removes it, `prune_excess_sessions` archives it together with its transcript, so no orphaned index is left naming a session the list no longer has); the chat side gains the `execution_round` kind plus the disposable `rounds.sqlite`; `intent-sessions.json` / `terminal-sessions.json` retire (**deleted in P5**: the single truth is the two `sessions`-table columns `intent_key` / `intent_closed` (SCHEMA_VERSION 10) plus the execution session's `chat_session_id` meta. The columns deliberately stay out of the `SessionMeta` struct, so `build_meta()`'s full upsert cannot erase a routing decision, and `upsert_row`'s explicit column list keeps the two writers from clobbering each other). **No compatibility work**: historical rows stay on disk and the renderer decides their shape — a legacy exec-sourced `agent_message` still reads as an ordinary agent bubble, while legacy `interaction_request` rows and `interaction_resolved` receipts are **hidden** (decided in P6: an old transcript must not resurrect an actionable card, since the write entry that used to answer it no longer exists). There is no migration. A pre-`round_id` session has no round index ⇒ the projection 404s ⇒ its block degrades to an explicit hole, not a lie.
- **Protocol**: new `GET /sessions/{sid}/rounds/{round_id}` (Runtime), `GET /api/chat-blocks/{chat_id}` (Gateway, **new top-level prefix**), `GET` / `PUT /internal/chat-sessions/{id}/rounds` (user internal surface), and `GET /sessions?chat_session_id=&surface=` (Runtime — the second `@` level reuses the one session listing with two query parameters; `/chat-candidates` and its Gateway proxy are deleted). The `/api/intents/chat-append` kind whitelist changes from `interaction_request|system_notice|agent_message` to `execution_round|system_notice|agent_message` (`agent_message` still carried the agent↔agent answer rows at P4; after P6 landed Decision 12 it remains only for the Chat Router's own answers). `mentions` gains `target_sessions` (the second `@` level, agent → session) and **`force_new_for` (a per-target list, not a flag — see Decision 7)**. The three addressing facts cross Gateway→Runtime as delivery `params` keys (`target_session_id` / `explicit_mention` / `force_new`, the two flags written only when true), so the ladder's first three levels need **no proto change**; `force_new` is a **per-target delivery parameter**, and the request body's list is only fanned out while assembling. The router's questions ride `system_notice`: `notice_type` is `session_choice` (level 3, ambiguous) or `confirm_continue` (level 5, proposal), with `options[]` plus `allow_new_task: true` in the meta and the idempotency key `{notice_type}:{author}:{inbound message_id}` (**Rev. 2026-11-06**: originally written `{notice_type}:{message_id}`, which dropped "which agent is asking" — a group `@A @B` is one row delivered to two routers, each asking about its own candidates, so keying on the row lets the first card swallow the second agent's question; `append_message` answers a repeated `message_id` with `already_written`, which its writer reads as success, and that `@` silently never gets a session) — an already-permitted kind, so no new write entry point. **Answering a card adds no protocol shape**: it is an ordinary re-delivery whose `message_id` is the original row's id (idempotent dedupe) plus the address fields. **`round_id` needs no protocol change** — Decision 2's derivation takes the inbound `message_id` as its only input; `Intent.for_execution_session` is already gone per Rev.8; `trigger_message_id` retires as a `TurnSurface` field and as the mirror writes' idempotency key in P4, while the same fact survives as the reference row's `in_reply_to`, supplied by `TurnReference` (see Decisions 2 and 3).
- **Deleted code**: Runtime's `exec_echo_meta` / `turn_routed_meta` / `router_fallback_meta`, the three `echo_terminal_row` sites, `write_interaction_card` / `close_chat_card*`, the surface back-fill patch (**all of it landed in P4 — the Runtime now has one chat write left, the reference row**); Gateway's `resolve_card_answer` / `mark_answered` / answer-row writes / the sweeper's chat failure row (becomes a notice), and the whole frontend `chatTurnState.ts` (with its `closedCards` bookkeeping), `InlineInteractionCard`, `ReplyQuote`, and `ChatNoticeEventRow`'s `interaction_resolved` / `answered` card-closure chain (**deleted in P6 — a card is only answerable once the block carries it and the answer goes straight to the execution session**; both Desktop views and Mobile's 1:1 surface gained the block renderer and the second level of the two-level `@` in the same batch). **Kept deliberately**: the render-time hiding set `RETIRED_NOTICES` in `ChatNoticeEventRow` (Desktop) and `ChatNoticeRow` (Mobile) — it is not mirror bookkeeping but the single implementation point of D14's "legacy rows stay on disk and are hidden while rendering"; deleting it would repaint today's reader the intermediate state of somebody else's past turn. **The same rule, applied per row** (the set can only be keyed by `notice_type`, while a row-level verdict needs the projection): an addressing card that a round has answered is an intermediate state of that turn, and the whole row paints nothing — the question was the middle of a turn, not a record of the conversation, and "which execution session took the words" is a fact the round's block states once (one fact, one place). Before this it had degraded twice: first into a row of disabled buttons, then into a "handed to <session>" receipt — both a second representation of the same fact, and the latter stacked into a column of identical lines, one per message. **Another per-row application**: a notice row left on disk that carries a row coordinate (`in_reply_to` naming a message still in the window) is the receipt of *that* message, so it paints in that participant’s column with an arrow pointing back at it; only a receipt with no coordinate — or whose subject has been paged out of the window — stays a centered channel fact. A centered failure receipt reads as a statement about the whole conversation, attached to nothing, while `delivery_failed` means precisely “this one message of mine did not go out”. The column comes from the coordinate alone: whether something was delivered stays `row.delivery`, and the presentation layer only decides a column, never a state.
- **Performance**: cross-process HTTP writes in the exec → chat direction go from "1–3 per turn, each with a 15 s write budget" to **0**; first paint issues one `GET /api/chat-blocks` (batched refs) and hits locally afterwards; cross-machine reads happen only on a miss. List and search paths still do zero projection reads (ADR-096 upheld).
- **Privacy and retention**: `rounds.sqlite` is a derived copy of execution-session bodies. It must carry the same encryption and retention policy as the chat main store and must be deleted with the chat (directory level). This belongs in the module-design storage inventory.
- **Rollback**: none is offered. Four surfaces plus the Runtime protocol change in one batch; rolling back means restoring both the mirroring writes and the pin mechanism.

## Acceptance (pinned by tests, not by convention)

1. **Zero write-back**: one chat-routed turn plus one execution-surface local turn must add exactly `{user_message, execution_round}` and `{execution_round}` to chat storage — asserting no write whatsoever in the exec → chat direction (the invariant behind `chatStore.execSend.test.ts` continues under its new shape).
2. **Natural-key dedup**: delivering the same `round_id` twice (replay / reconnect) produces one reference row.
3. **Lies are unconstructible**: cut the Gateway→Runtime projection read and the block must show unreachable; no path can leave "in progress" stuck forever, because the write that could fail does not exist.
4. **Disposability**: deleting, corrupting or tampering with `rounds.sqlite` only causes a re-fetch; chat reads, writes and pagination are untouched.
5. **Rounds are not inferable**: the four counter-examples of Decision 2.
6. **Addressing priority**: levels 1 and 2 never reach the LLM; a level-5 proposal produces a confirmation card and does not deliver.
7. **Redlines**: `run_gateway_fs_redline` and `run_session_full_read_redline` are simultaneously green; the `/api/chat-blocks` read path never performs a full exec JSONL scan.
8. **The three permission layers**: a non-participant reading a block gets 404; a participant may read; a non-initiator pressing a button is refused.
9. **Cross-chat poisoning is impossible**: a ref naming another chat's execution session yields neither content nor a cache write (it becomes `not_found`); forging a chat-scope header cannot rewrite the projection's `chat_session_id`, because the binding is read off the session meta on disk.
10. **A wrong coordinate never becomes content, and a bad ref does not contaminate**: when the transcript changed after the side table noted its coordinates (a line rewritten, a transcript absent), the projection must answer a hole because the row's own `round_id` stamp does not match, and must never return whatever sits at that position; one malformed ref or `round_id` spoils only its own slot, while every other block in the same request is served normally. A round with no `answer` coordinate must not fold the next round's attachments into its block.
11. **A momentary read fault is not "it never happened"**: a batch item carrying `found: false` plus `error` surfaces as `unreachable` (retryable), which keeps it distinguishable from a permanent `not_found`.

## Revision (2026-11-03): the wait line's positive evidence extends to this device's own send claim (restating Decision 9)

When Decision 9 landed, the human row's wait line shrank to "the POST this surface has in flight" (`sending`). The boundary was right; the length was wrong. A POST round-trip measures about 150 ms and proves only that **delivery landed**, while that round's first durable row was observed 0.008 s to 81.3 s later. So the seconds-to-minutes between sending and the agent speaking showed nothing but a blank transcript, and the composer became available again at the same moment — the reader concluded "my message did not go through", and could push a second sentence before the first one had a landing point, even though no chat-level queue exists. ADR-100 D6 (the transient frontend send placeholder), kept by Decision 14, is exactly the window this revision hands back to it, without breaking Decision 9's shape.

The credential's lifetime is extended from the POST round-trip to "this sentence has a landing point in the transcript". **The shape of the predicate does not change**: still positive evidence, still only this device's own send, still never an inference over how rows are arranged.

- **One source of truth**: `inflight[chatSessionId] = { messageId, at }`, in memory only, written only from **this device's own send response** (the id the Gateway gave the human row), never derived from row order or row kinds.
- **A claim is armed when the sentence was actually taken**: 1:1 `POST /api/intents/chat-message` answering `status === "delivered"`; for a group, `POST /api/intents/mentions` arms a claim if **any** entry of `results[]` is `delivered`, keyed by the **top-level** `message_id` — one row, N deliveries, and it is the row that owes the answer, not one delivery of it. `routed: "archived"` and an all-failed fan-out arm nothing: a send with no receiver owes the transcript nothing, and waiting for it fabricates an outcome; the same holds for a 1:1 `failed` (the `budget_exhausted` limit receipt is a different outcome, and it is visible on its own).
- **Settled** by the first row carrying `meta.in_reply_to === claim.messageId` whose kind is one of `execution_round`, `agent_message`, `system_notice`; notices the surface hides via `RETIRED_NOTICES` are not a landing point (two ids on Desktop, five on Mobile, each aligned with that surface's own hidden set). A group's `delivery_failed` receipt is therefore precisely the row that settles the claim — "a failure must be visible" and "a failure ends the wait" turn out to be one rule, not two.
- **A 300 s deadline** (the same order as the sweeper's timeout) releases the claim when the outcome row never arrives. Release matches on messageId, so a late settle or expire can never clear a successor send. "In progress" is thus **a claim with an expiry date**, not a fact derived from missing rows — which is what separates it from ADR-100 D10 and what keeps this revision inside Decision 9.
- **One claim drives both the wait line and the composer gate** (`turnInflight` ⇒ `composerLocked`): the next sentence cannot be sent until the previous one has a confirmed landing point. The lock is honest presentation, not a disguise for queuing — there is no queue in the system, so a second sentence is not accepted; while locked, the send button is disabled and says why (`chatView.notice.turnInflightTooltip`).
- `sending` returns to its original meaning: a POST is in flight. It is no longer the wait-line or lock signal.

**Unchanged boundaries** (recorded so this revision is not misread as a return to negative evidence): the wait line does **not** infer liveness from "no terminal row follows the newest human row", and does **not** read `auto_routed_to` / `mentions`; after a reload or reopen there is no wait line — this device has no send of its own to claim, which is Decision 9's first-person discipline, not a defect; a claim covers one sentence on one session on one device, so how far that agent round got is irrelevant to it, and once a landing point appears the human may send the next sentence immediately even while the round is not terminal; the block's `pending` read (Decision 9's first bullet) is untouched, because the two speak about two different objects. No backend protocol change.

Where it lives: [chatTurnInflight.ts](../../../apps/acowork-desktop/src/lib/chatTurnInflight.ts) and its same-shape Mobile twin [chatTurnInflight.ts](../../../apps/acowork-mobile/src/lib/chatTurnInflight.ts); the claim is written in both stores and the deadline timer lives at store module level (it does not depend on a surface being mounted — the surface only settles). Wired into Desktop's `AgentChatView` / `GroupChatPanel` and Mobile's `AgentChatScreen`. Rewritten in the same pass: this ADR's Decision 9 wording, [ADR-105](./ADR-105-group-default-responder.md)'s D4 supersession note and the D5 status note about the receipt ending the wait, and design 27 §5.3.1 and §5.5.5 items 2/3.

## Revision (2026-11-03): the round doorbell restores the notification face Decision 3 removed

The defect shape: `@` a session from a chat, the execution session enters running; the reader stays on the chat surface, the round finishes, and the block keeps saying running. Opening "view execution" shows it already done; only switching back to the chat refreshes the block to Done. In other words, sitting on the chat never learns the terminal state in real time.

Both root causes are the same one, and both are this ADR's own bill:

1. **Decision 3 made `exec → chat` a zero-write path and removed the notification face with it.** Under the mirror, "the terminal row was written" was itself the notification — the writer learned the round had ended as a side effect of writing it. After zero-write, Decision 5's cache is deliberately built to hold only terminal projections with **no invalidation path** (that is its virtue: no invalidation protocol needed), so the block's only recovery is to re-read — and this ADR never said who triggers that re-read. Acceptance item 3 guarantees no in-flight state stranded by a failed write; it does not guarantee no in-flight state stranded because nobody re-reads.
2. **The frontend's re-read was armed wrong.** `useChatBlocks` re-read pending blocks with a one-shot `setTimeout`, re-armed by the effect deps `[chatId, key, anyPending, reload]`. Zero-write means those deps never change — the terminal row used to be the one thing that changed them. So once the timer fired it was never re-armed, and only an unmount/remount restored it, which is exactly why "switch away and back" fixed it.

The backend was innocent: the on-disk side table recorded the same round non-terminal at 09:02:43.370 and terminal at 09:02:43.378 — 8 ms apart. What needed fixing was the notification face, not the projection.

**Decision 1: add a `round_state` doorbell event.** Proto shape `RoundStatePayload`, attached to the `SessionMessage` oneof at field **34** (33 was the highest used field at the time). The chain copies every existing session event rather than opening a channel: `AgentLoop::close_turn_round` publishes after closing the round (the round id must be captured **before** the closure, because closing clears the writer's active round) into the per-session chunk channel → `relay_chunk_event_mqtt` (awaited one by one, so call order equals broker enqueue order) → `MqttChunkPublisher::publish_round_state` → topic `acowork/agents/{instance_id}/sessions/{sid}/messages/round_state`, **QoS 1, non-retained**. The payload carries two coordinates only — `round_id` and `chat_session_id` — and neither content nor an outcome word (Decision 4 unchanged).

- Its meaning is **"worth re-reading now"**, not "here is the final content": the event fires at the turn boundary, while the round's terminal record is a separate append by the session's single writer (ADR-092), measured about 8 ms later. Readers must therefore allow one bounded retry (500 ms) and treat "still pending" as normal, not as a failed signal.
- It also covers a round parked on a card, over the same bell as a terminal one: `close_turn_round` does not distinguish them, so the block re-reads, reads `waiting`, draws the question and **keeps** showing the round as in flight. That branch had zero notification as well — it is the same hole, not a second one.
- **Why the outcome word stays off the wire**: no subscriber can act on it without the re-read anyway (every subscriber needs the body to draw the block, and the word arrives with that read), while adding a proto3 field later is free. Shipping a speculative field today only widens a public contract — plus the hand-written decoder (`proto-wire.ts`) that must track it — to a reader that does not exist. The doorbell's responsibility boundary is therefore "which block, which chat".
- **This does not contradict the rejected alternative "open a new realtime channel for the projection".** That was rejected to avoid a second piece of live truth. This event carries no content and cannot change any projected value; it is only a re-read trigger. The live truths remain `session_state` and the projection read.
- **The field number is a cross-repo contract.** Mobile ships no protobuf runtime — its wire reader is hand-written (`proto-wire.ts`), so a Rust unit test pins field 34's tag and proto3's default-omission rule: a silent renumber in the `.proto` must break a test, not strand every block on "running" forever.

**Decision 2: demote the periodic re-read to a dropped-frame backstop.** The pending re-read becomes a `setInterval` (this is the root-cause fix: arming is now symmetric with unmounting), and its period widens from 4 s to **15 s** — it is no longer the main path, it only closes rounds whose doorbell frame was lost. A doorbell that hits a **mounted** block reloads it immediately, with one bounded retry; if nothing is mounted, nothing happens (mounting reads anyway).

**Where to subscribe**: Desktop already has the wildcard `acowork/agents/+/sessions/+/messages/#`, so zero new subscriptions. Mobile's `realtime.ts` holds the design 25 §8.0 **single-session exact-subscription** invariant, and giving it a companion subscription would break that shape, so the doorbell rides on `presence.ts` — which already wildcard-subscribes `agents/+/status` and `agents/+/sessions/+/state`, and the event being non-retained means subscribing replays nothing. A third option was rejected: having the execution session publish into the chat's topic tree — it depends on permissive broker ACLs and breaks the "topic ownership is session ownership" discipline.

**Decision 3 (added 2026-11-05): the doorbell's second trigger — a card opening or closing inside a live turn.** The defect shape: the execution session raises an `ask_question` card and blocks on the human, while the Chat's block for that round shows no card at all. Measured evidence (one round; the on-disk side table plus the Gateway request log): the card was recorded at 22:22:21 (`card` + `status=waiting`) and retracted at 22:23:15 when it was answered, and the block read for that ref happened only at 22:22:17 and 22:23:37 — **for the whole life of the card the Chat read nothing**. The projection was never missing a field; the notification surface was missing a trigger. `publish_round_state` was called only from `close_turn_round`, while these two card kinds open and close inside a turn, so neither end of the transition touches the turn boundary; and the 15 s interval backstop was eaten by webview timer throttling while the window is occluded (the log shows an earlier 28 s dropped frame as corroboration).

The fix: `publish_round_card_state` — the single point both `track_interaction` (open) and `forget_interaction` (retract) pass through — now states the side table **and** rings the doorbell. Three deliberate details:

- **Same order as the write**: `note_round_state` first, bell second. The bell only means "worth re-reading", and the writer's few-microsecond lag is absorbed by the reader's existing bounded 500 ms retry — the same mechanism the turn-boundary bell already relies on, with no protocol change.
- **The bell names the round the write hit**: `Conversation::note_round_state` therefore returns the `round_id` it wrote for (`None` when no round is armed, and then nothing rings). `active_round_id()` is unusable here: it reads the writer's tracking, which only learns a round after processing that round's first row — and "turn just started, question first" precedes exactly that.
- **Retraction rings too**: otherwise the Chat keeps offering a button for a question that was already answered — a second and wrong representation of one fact.

**Decision 9's discipline is unchanged**: the doorbell establishes no liveness and is not an evidence bit for "in progress" — it triggers one read, and the `terminal = false` that read returns is the predicate. This distinction is written down because without it the event would be read as the very thing it just replaced.

## Revision (2026-11-04): the presentation contract forks on `opened_new`; the act space becomes the `exec_session_*` family with a read-only `exec_session_read_round`

**Revision 1: the folding rule forks on `opened_new` (presentation contract).** The defect shape: the user message that opened a fresh execution session vanished into the block as a folded trigger row — a new session appeared right beside the words that created it with no visible pairing at all, so the block read as an orphan talking to itself instead of half of an exchange. Continuation rounds never had this problem: their antecedent is the previous round's own output in the same session.

Therefore: when a reference row carries `meta.opened_new === true` and has a trigger row, that `user_message` is **not** claimed by the block — it stays a standalone user bubble, and the layout reads "question, then block". Continuation rounds (`opened_new` false or absent) keep folding, and the "one sentence, one place" discipline holds in both branches: the opener round's line inside the block leads with the `assignment_brief` (D13: always a presentation hint) instead of painting a question panel over the trigger's text again, falling back to the round projection's `user.body` (truncated) when there is no brief. The block header still derives its title from the trigger row (the layout keeps the `triggerRow` reference for that alone), and the locate map now points an opener trigger's seq at its own bubble rather than the block. Zero data-layer change: the `user_message` row was always persisted by the Gateway before routing — the fork lives entirely in presentation. Implementation: Desktop's and Mobile's `chatTranscriptGroups` gain the explicit marker `questionOnTranscript` (distinct from a fan-out's `showUserLine = false` — both mean "do not repaint it inside the block", for different reasons), and the claim set, the block's seq list, and the locate map follow the marker; the pinned-window rule ("never hide a round carrying this chat's own question") no longer needs the fold for openers — the sentence is already visible on the transcript. Both surfaces implement the same rule, so the contract cannot drift apart.

**Revision 2: Decision 6's act space is renamed to the `exec_session_*` family.** `new_task` → `exec_session_create`, `propose_existing` → `exec_session_propose_continue`: the names describe the object operated on (an execution session), not the model's subjective judgement. The authorization edges of both acts are unchanged word for word — the first remains the only delivery the model may perform and can only create, the second remains a proposal with a confirmation card, `why` required, with level 5's cheap escape. The old names join `dispatch` in `RETIRED_ACT_NAMES`' drift guard, so the kernel prompt can no longer teach them; the confirmation card's wire field `allow_new_task` is a protocol shape, not a tool name, and does not change.

The same batch adds the read-only act `exec_session_read_round(target, rounds)`, the missing legitimate source for "how did that task turn out": `target` takes a candidate from this turn's alias table (the permission-filtered set — no new authorization surface), `rounds` clamps to 1–3; it reads exactly the Decision 4 round projection (sidecar fold + two bounded row reads + the attachment-window endorsement), disk-only so Closed sessions read fine; the result lives only in this turn's tool_result and is **never written to durable** (reference rows stay bodyless, Block B still does not project round content); every failure is an explicit hole in the tool_result text, never a whole-turn degrade. The safety tail relaxes accordingly: from "never claim what an execution session did" to "you may report only what `exec_session_read_round` returned this turn; never claim what an execution session is doing or will do". There is **no `exec_session_send_msg`**: addressing stays with the human, and this revision does not reopen Decision 6's silent-delivery ban. The rename and the prompt/tail literal changes cost one provider prefix-cache miss — expected; for the hard context/caching constraint see Design 29 §11 (execution-session information enters the context through exactly two doors — Block C's dynamic region, or Block B's seq-deterministic projection — and the presentation layer's visual re-layout never feeds back into the projection order).

## Revision (2026-11-04): `@` on an execution session is fixed as reference; continuation moves into the block's inline input box

**Motivation.** The trigger was a real scenario: the human gives one agent two parallel execution sessions, and when both finish, wants their results summarised into a new session. The current wire cannot express it — `target_sessions` is a `HashMap<agent, session_id>`, so each agent can be named for exactly **one** session, and N references have no footing at level 2. The first proposal was a count fork — "one `@` = forward, N `@` = reference" — and it was rejected: one symbol carrying two intents is wrong modelling, because with a single `@`ed session the human may equally just want to cite its conclusion and open a new session; the count is not a predicate for intent. The final design separates intents **by medium** instead, into three orthogonal slots: who this sentence is for (`@agent` / direct-chat default / group `default_responder` — unchanged), where this sentence goes (the **block's inline input box** → ladder level 1), and what material this sentence carries (`@session` → `meta.refs`). `@` keeps exactly one meaning, and level 2's delivery duty moves wholesale to level 1 — which was already in the architecture (`in_reply_to` pointing at an `execution_round` ⇒ deterministic continuation). The block input box is not new semantics; it is the physicalisation that compresses level 1 from two steps (borrowing the main composer) into one.

**Ruling 1 — `@session` = reference material (1..N, one intent).** The persisted human row carries coordinates only: `meta.refs = [{agent_instance_id, session_id, round_id}]`, resolved and **pinned at send time** by the Runtime to each session's newest terminal round within its permission-filtered candidate set — the coordinate is the fact, the content is the projection; if the referenced session keeps running afterwards, this reference's snapshot does not rot (terminal rounds are immutable), which extends "references, not copies" rather than betraying it. **No round body is ever written to durable.** Presentation: references render as chips on the human bubble, clicking one locates the source block (the "note where this came from" need is carried by the coordinate plus the chip, not by assembled prose). When the router assembles, it reads the projections in-process by coordinate, and the execution arm **reuses `exec_session_read_round` wholesale** (sidecar fold + two bounded row reads, the 2KB/512B clamps, every failure an explicit hole, never a whole-round degrade), rendered into **Block C's dynamic region** — on the legal road of design 29 §11's hard caching constraint, never in the cached prefix; beyond the per-reference clamps the reference set passes one aggregate budget (Block C bloat feeds directly on the router's token budget; references clamp to 1–5). If a referenced round is still running (no terminal round to pin: take the in-progress round at that moment, labelled `terminal=false`, "progress as of then"), and an unreadable one is a hole. On delivery the content is **materialised as an ADR-107 reference part** (kind `referenced_round`, riding `params.context_refs` with the message, the source coordinate written into the markdown body) — the execution side cannot read the chat nor other sessions' rounds, so the material must ride along; it takes the same channel as the `chat_background` brief, keeps the `user` row as the human's own words (ADR-046 §2.1) and unpolluted auto-titles — a one-shot delivery materialisation, not a resident copy; addressed-continuation deliveries (including card-answer re-deliveries) carry it the same way. **The recipient does not change**: refs are riding material, they do not decide who the sentence is for — a direct chat naturally goes to the counterpart agent, a group falls to `default_responder` as before; implementations must not treat refs as addressing. A message carrying refs **skips the ladder's continuation branches** (level 3's auto-delivery and choice card both stay silent, exactly like `force_new_for`) — material means "new work or chitchat", never continuation; continuation is the block input box's job. `target_sessions` retires **from the human-`@` path**, replaced by `refs`; **answering an addressing card keeps that channel** — the reply to a level-3 multi-candidate choice card or a `confirm_continue` confirmation IS an address the human chose (the machine asked, the human answered), consistent with "addressing belongs to the human"; what this revision retires is the typed-`@` delivery path, not that decision. `force_new_for` stays a per-target list, unchanged. Validation follows `validate_mention_addresses`' "never guess, 400 outright" discipline: every `agent_instance_id` in `refs` must be among this message's `targets` (a reference must hang off an addressing act; an orphan reference is illegal). The kernel prompt gains a `[referenced rounds]` section with reading rules ("material attached by the human, used to decide whether to `exec_session_create` a summary"), pinned by the drift guard; the prompt byte change costs one provider prefix-cache miss — expected.

**Ruling 2 — the block's inline input box = the physicalisation of level 1.** Sending from it writes a `user_message` carrying `in_reply_to` (anchored at the block's `execution_round` row `message_id`) through the same POST — ladder level 1, idempotency and the wait line all exist; zero new semantics. Reveal discipline (Desktop): the box appears when the cursor enters the block (hover/focus) and disappears when it leaves; the iron rule is **never collapse while the draft is non-empty or the box holds focus** (otherwise typing loses characters) — only "empty + blurred + pointer gone" hides it. Mobile has no cursor; the substitute shape is a **resident lightweight input row at the bottom of an expanded block**, never present when collapsed — one rule on both surfaces, presentation density may differ (the same discipline as the Mobile paragraphs of the D3/D4 presentation contract). The send side keeps the 2026-11-03 wait-line revision: a block-box send owes **this device's claim** just the same (per-chat landing), with the wait line and composer gate settling on the claim, not sharing the main composer's in-flight state. Permission (the same shape as Decision 10's third layer): **only the round's `answerable_by` may use it**; other members see a disabled box with the reason — without this layer, a group member could continue somebody else's session through the box, handing back at the UI exactly the power Decision 6 just took away.

**Ruling 3 — sessions outside the loaded window lose direct delivery: an open trade-off.** Level 2 used to backstop "the addressable set is larger than the transcript window": Decision 7's "a session you never page to is still in the transcript, reached by replying to its block" presumes the block is always reachable, yet block anchors exist only inside loaded windows and long histories paginate. After the redrawing, continuing a session whose block has scrolled out of the loaded window has exactly one road: page back to the block. This revision openly adopts the two-step answer: first, accept it (long-lived sessions' blocks are usually reachable via recency anchors; if one truly cannot be found, the human should recover the target through the transcript / `exec_session_read_round` anyway); second, every row of the picker's second level gains two actions, **"reference / go continue"** — the latter delivers nothing, it just locates that session's block anchor (the mechanism exists) and focuses the block's input box, turning the gap into two steps instead of a new delivery channel. The rejected third option: keeping `target_sessions` as a delivery channel alongside the new `refs` — that is a return to two channels and defeats the point of this redrawing.

Landing points: the Gateway's `POST /api/intents/mentions` and `chat-message` wire (`target_sessions` retiring from the `@` path and staying for card answers only; `refs` added, the 400 discipline, round pinning at send time), the Runtime's `rounds?latest` read endpoint, the prompt section and drift guard, Block C assembly, delivery materialisation (the ADR-107 `referenced_round` part), the two-level `@` picker's reference mode, and Desktop's and Mobile's block input-box components (reveal/focus-trap discipline, claim, Decision 10 disabled state) plus the transcript chip presentation. Synchronised in the same batch: this ADR's Decision 6 ladder table and Decision 7's level-2 annotation, design 27's presentation sections, design 29 §11's reference-material assembly rules, and the [HTTP protocol](../../protocols/en/http.md) mentions contract.

## Revision (2026-11-05): the index precedes the reference — "visible ⇒ answerable", and an empty round reads as pending, not as a hole

**Motivation.** A real failure: the human sent a message from the execution block's inline input box, the message did reach the execution session and the agent answered normally, yet the block in the chat said "this run is no longer available" (`chatView.block.notFound`). Logs and on-disk state showed an **ordering gap** between Decision 3 and Decision 4:

- 01:48:43.095 the Gateway accepts `chat-message`; at the turn boundary the Runtime writes the Chat's `execution_round` reference row (Decision 3);
- 01:48:43.113 the Desktop reads the block projection for `refs=…|r:42590fc9…` — **triggered by exactly that reference row**;
- 01:48:43.151 the read answers `found:false`;
- 01:48:43.170 the round's first side-table record lands (`{"round_id":"r:42590fc9…","user":309,"terminal":false}`); the same millisecond the Runtime logs `Idle→LlmAwaitingFirstChunk`;
- 01:48:47.160 the round closes `terminal:true, status:"completed"` — the reply arrived normally;
- the ref was **never requested again** (one request in the whole log).

The mechanism: a side-table record used to appear only once the round's **first `round_id`-stamped row was committed** (`ActiveRound::snapshot()` wrote `self.user.unwrap_or_default()`, which is why the writer refused to snapshot while `user.is_none()`), while the reference row became visible before that. A read landing in that ~60 ms window was classified `Hole`, and the client treats a hole as the block's permanent content (Decision 5: nothing re-reads a terminal result) — a finished run was declared dead. This is not incidental: Decision 4's reader is *triggered* by the reference row, so the read lands inside the window by construction.

**Ruling 1 — the round index precedes the reference row (`announce`).** Before writing the reference row, the turn boundary registers the round in the side table (`rounds::announce_round`, through the writer thread's synchronous `WriterCommand::AnnounceRound`, which returns only after the line is flushed). That yields the new invariant: **every round the Chat can see, the index can answer**. The announcement line carries no coordinate (`user` absent) and no `status`: how the turn is doing is the turn's fact, not the index's — the line only states that the round exists. Announcing a round that is already recorded is a no-op that never rewrites coordinates (a redelivery or a continuation must not erase what the transcript already says).

**Ruling 2 — `RoundRecord.user` is optional, and a recorded round is never a hole.** Decision 4's record shape is amended to `{round_id, user?, answer?, card?, terminal, status?, ts}`, where an absent `user` means "announced, opener not written yet". `project()` answers such a record with `{user:null, answer:null, terminal, status}` — a non-terminal projection (the Gateway's `pending`, which the surface re-reads per Decision 9, so the block fills in as rows arrive) instead of a hole. A hole is thereby reserved for two facts only: the transcript is not on this host, or a coordinate has drifted and no longer names a row of this round (Decision 2's stamp check is unchanged). The opposite edge is tightened as well: the writer no longer needs a coordinate to publish a terminal snapshot (`RoundSnapshot` checks round identity only), so "the turn died before writing its opener" still lands `terminal:true, status:"failed"`, and a content-less round pre-empted by a later one is closed as `interrupted` (`forced_closure` no longer requires a coordinate) — a block that can never settle is a different lie.

**Not doing (boundary).** No "re-read on `not_found`" on the client: that would be an admission that the server may produce false holes, i.e. putting the invariant in the wrong layer. Cache semantics are unchanged (Decision 5: terminal is immutable, no invalidation path); what changes is the source of the fact behind "terminal".

Landing points: `core/acowork-runtime/src/rounds.rs` (`RoundRecord.user: Option<u64>`, `announce_round`, the coordinate-less branch of `project`, `forced_closure`, the `fold_attachments` signature), `core/acowork-runtime/src/conversation.rs` (the synchronous `WriterCommand::AnnounceRound`, `ConversationSession::announce_round`, the relaxed `RoundSnapshot` guard, the writer-side tracker hand-over), `core/acowork-runtime/src/agent/loop_.rs` (`open_round` order: `announce → reference row → stamp`). Acceptance is pinned by tests: `an_announced_round_projects_as_open_instead_of_a_hole`, `announcing_a_known_round_keeps_its_coordinate`, `a_round_closed_before_its_opener_is_not_a_hole`, `an_announced_round_reads_as_open_not_as_a_hole`, `an_announced_round_is_answerable_before_its_first_row`, `a_pre_empted_announcement_is_closed_not_left_open`. Neither the Desktop nor the Mobile block renderer needs a change (`projection.user` is already optional on both sides; an empty user falls back to the existing "no question / in progress" copy).

## Revision (2026-11-06): a failed delivery is no longer a chat row — an in-memory live alert (with a Decision 12 / 14 amendment)

**Motivation**. Real defect: after a failed delivery the chat kept a yellow `system_notice` (`notice_type: "delivery_failed"`) that stayed **forever** — after a successful retry, after the agent was installed, on every reload, on every device, in every old backup. It also counted as "this message has been answered" in `acowork_core::intent::chat_kinds::is_answer_row`, so a long-dead failure went on announcing an outcome for that message. A log records who said what to whom; a momentarily broken link is not conversation content.

**Decision**. `delivery_failed` **has no writer any more** (ADR-105 D5, revised): the failure became an in-memory alert hanging off the **read model** — `acowork-user`'s `ChatAlertStore` (`(chat_session_id, row_id) → {target, error_code, inserted_at}`, 600 s TTL, gone with the process, nothing persisted). The Gateway's three failure branches and the sweeper's timeout fallback post to `POST /internal/chat-sessions/{sid}/alerts`; the read side decorates the human row the delivery owed as `ChatRowView.delivery.alert` (`{target, error_code, expires_in}`), and each surface schedules its own removal. Desktop and Mobile paint it with `DeliveryAlertLine`, and `RETIRED_NOTICES` gained `delivery_failed` so old rows disappear at render time.

**Effect on Decision 12**. The vocabulary conclusion stands (chat records conversation); one member left the "channel fact" class: the live `system_notice` writers that remain are the three limit receipts (budget / truncation / unreachable) and the two addressing questions. `THREADED_NOTICES` keeps `delivery_failed` — not because it still has a writer, but because **the rows in old transcripts are exactly it**; a vocabulary that forgot it would turn those rows into unexplainable data.

**Effect on Decision 14**. The "old rows stay on disk, hidden at render time" mechanism applies unchanged, with one more member in the hidden set: a failure that is over must not keep occupying the page — the same rule as "a milestone is not history". The row-level `delivery.alert` takes **no** part in settling-style inference: it is a time-limited state, not a receipt row.

**Boundary**. No persistence for the alert and no "read" state: its entire value is *now*. Zeroing on restart is correct behaviour — after a restart "it just failed" is no longer new.

Landing: `core/acowork-user/src/chat_alerts.rs` (new), `core/acowork-user/src/chat_view.rs`, `core/acowork-user/src/http/chat_sessions_api.rs` (internal route), `core/acowork-gateway/src/intent/chat_client.rs`, `core/acowork-gateway/src/http/intent_api.rs`, `core/acowork-gateway/src/intent/sweeper.rs`, `core/acowork-core/src/intent.rs` (`RETIRED_NOTICES`), and Desktop/Mobile `DeliveryAlertLine` / `ChatNoticeRow` / `chatTurnInflight`. Pinned by tests: `chat_view::tests::a_live_failure_is_a_decoration_of_the_row_it_concerns`, `chat_sessions_e2e::unaddressed_group_message_reaches_the_default_responder` (asserts no receipt row and a live `delivery.alert` on the row), the self-expiry cases of `DeliveryAlertLine` on both surfaces, and the alert branch of `turnInflight`.

## Revision (2026-11-06): a terminal round carries no non-waiting card; answering a block card forces a re-read

**Motivation**. Real defect: an `ask_question` card popped by an execution session timed out after 300 s, and the same card *projected into the chat* **did nothing when clicked and never disappeared** until a new message covered it, while the same card in the execution session behaved correctly. The same bug came with a layout problem: the chat-side options were one horizontal row, which collapses on long option text.

**Root cause (verified through logs and `rounds.sqlite`)**. Three layers each left a gap:

1. **Writer**: after the 300 s timeout, `forget_interaction` nulls that round's `card` and writes `terminal=true, status=in_progress`, but the **pre-emption path** (`forced_closure`) and **crash repair** (`repair_on_open`) kept the old `card` value, so a terminal snapshot still carried a card that was not `waiting`.
2. **Reader**: the Gateway's `chat_blocks` paths (cached and live) served that projection verbatim with no consistency pass — and a cached entry never expires (D5: terminal is immutable), so the wrong value was frozen in.
3. **Client**: after a successful POST, `BlockCardActions` only cleared the card locally (`resolveQuestion`) and never re-read the block; within `noteRoundState`'s bounded 500 ms retry window the block could still be `pending`, and afterwards no signal triggered a re-read, so the card stayed in the projection forever.

**Decision one (writer invariant)**: **a terminal round must not carry a card that is not `waiting`**. `forced_closure` clears the card when the round already has one and `status != waiting`; `repair_on_open` does the same for an open round. A card is the evidence that "this round is waiting for a human"; once a round has closed, it cannot still be waiting.

**Decision two (reader convergence)**: in `assemble`, the Gateway runs both the `Cached` and the `Live` path through `served_projection`, forcing `card: null` when `terminal=true` and `status != "waiting"`. The cache exists to save a read, not to preserve a wrong value on the service's behalf; the writer invariant is the first line and reader convergence the second — not redundancy, but the backstop for old data and outside writers.

**Decision three (the client does not guess)**: after a successful card answer, the surface must call `useChatBlockStore.getState().reload(chatSessionId, [ref])` in addition to its local clear. An answer is a change of fact; the presentation layer has to read the server's fact rather than trust its own optimistic state. Pinned by `answering re-reads the round, whatever the POST said`.

**Decision four (layout)**: `ask_question` options in the chat-side block are stacked vertically (`flex flex-col items-stretch`), while the two approval buttons stay horizontal — options are *sentences* and their length is not ours to control, so a horizontal row is guaranteed to break on long copy.

Landing: `core/acowork-runtime/src/rounds.rs` (`forced_closure` / `repair_on_open`), `core/acowork-gateway/src/http/chat_blocks.rs` (`served_projection`), `apps/acowork-desktop/src/components/chat/ChatExecutionBlock.tsx`. Pinned by `crash_repair_drops_the_card_of_the_open_round`, `a_waiting_round_keeps_its_state_when_pre_empted`, `a_cached_terminal_card_is_not_served`, `answering re-reads the round, whatever the POST said`.

## Revision (2026-11-06): the block action row and the reply drawer (presentation layer)

**Motivation.** Revision 2 of 2026-11-04 put the in-place continuation at the **bottom** of the block while "view run" stayed a pill **above** it — one object wearing an interaction band at each end, which reads as two objects; and the bottom field reserved its height even when nobody used it, pushing the rest of the transcript down. The ruling: an action belongs in one row next to the thing it acts on, and an input appears only while it is being used.

**Decision 1: four actions, one icon row above the block** — view run (drill into that execution session), `@` reference, copy the whole block, continue. Icon-only keeps the row from growing wider than the block header; the price is discoverability, so every control keeps an `aria-label` + `title`, and the view-run tooltip carries the session's NAME (the standing rule: a fixed label repeating the glyph says nothing). The row is always visible — a control only a pointer can find is a control most humans never learn about.

**Decision 2: the reply drawer.** The message button is its own capsule: hover, focus, a non-empty draft, or the locate signal's rising edge slides the field open to its right, with the icon staying at the capsule's left edge — visually "the field wraps the button". Three mechanical constraints are load-bearing: (1) the row's height is fixed (`h-6`) and only `max-width` transitions, so opening never moves the transcript; (2) the field inside keeps a FIXED width while the capsule clips it — a child re-wrapping every frame is exactly what makes CSS drawers jitter; (3) closed means `inert`, so the clipped field never sits in the Tab order. It closes only when the pointer has left AND the field is unfocused AND the draft is empty, and a pointer leave is deferred ~100 ms so a cursor crossing the row cannot strobe it. The `@` picker's "go continue" and a source-chip click ride the same locate: open first, focus on the next frame (focusing a zero-width field scrolls the row sideways for one frame).

**Decision 3: `@` reuses the reference-material channel.** The block's `@` invents no new semantics: it pushes `{agent_instance_id, session_id}` into the address state the main composer already owns (`ChatRefPick` → a removable chip), keeps the server's 1–5 ceiling (the sixth answers with a hint instead of silently dropping the click), and is idempotent for a run already attached. Because a level-1 reply already carries its own session coordinates, clicking `@` releases the reply target first — two contradictory instructions must not ride one send (the send path refuses them; the presentation layer must not make that look possible).

**Decision 4: copy is a Markdown export.** Its content is the session name plus each round's question/answer, **including the rounds the block keeps folded** (the button says "this execution session", and a document that starts at round six misrepresents the run); a round whose content cannot be read is exported as a stated hole, never as an invented answer (Decisions 3 / 5); an answer body is pasted verbatim so its own fences and tables survive. Success wears a brief checkmark (`CodeBlock`'s existing habit); a failed copy never reports success.

**Scope.** Both Desktop chat surfaces (1:1 `AgentChatView`, group `GroupChatPanel`) share one action-row component; a read-only session (`canAnswer=false`) hides `@` and the drawer while copy stays available (a read). Mobile has no hover and keeps its in-bottom-of-block field; this revision does not touch it.

## Revision (2026-11-06): the block anchors at its first appearance; the addressing card lands at the block's tail (presentation layer, D4 contract)

**Motivation.** D4's presentation contract asks that an execution session appear in the transcript exactly once, and v3.1.1 realised that as "anchored at the session's **newest** reference row in the loaded window". That anchor contradicts its own intent ("the freshest answer stays next to the freshest question") under real use: a session outlives the turn that opened it, every continuation inside this Chat adds one more reference row, and the block is dragged past every row written in between — after a few exchanges the human's messages are stacked at the top and the block answering them has fallen to the bottom, so the paired back-and-forth is gone. What the anchor bought — "the newest is visible" — the block's own window already provides (it opens to the last 2 rounds).

**Decision 1: anchor at the session's oldest reference row in this window.** Position belongs to the exchange, not to its latest round; a continuation adds rounds and a round count, never a position. Nothing becomes less readable: the block expands its newest 2 rounds and scrolls, `keyOfSeq` still maps every folded seq to the block (a locate on a new round lands on it), and the virtual list's item identity moves from "newest row" to "first row", so the block is no longer rebuilt — height cache included — on every round.

**Decision 2: compute the mapping, then walk.** The old layout wrote `keyOfSeq` while walking the rows, so a folded row standing after the block that folded it overwrote the block's own entry with the row's key — a locate then pointed at a row that is not in the DOM. It only held because the block was always last (it sat at the newest row). Moving the anchor exposed it. The mapping is now resolved before the walk, and the walk only emits items: order is a layout choice, and the mapping must not inherit it.

**Decision 3: a `confirm_continue` question lands at the tail of the block it asks about.** The router's proposal asks about **one** session (its `options` name a single target); drawing it at the transcript's newest position asks the reader to answer a question whose subject is off screen, and a fixed anchor only widens that distance. It is hung on that block's tail (only when `options` name exactly one target and this window holds exactly one block for it; a multi-candidate `session_choice` has no single target and stays where it stands), visible while the block is collapsed too (D8: something answerable behind a fold is not answerable), with the existing answerability rule (who opened the round, `mayAnswerCard`).

**Decision 4: updates move the viewport, not the block.** On the frame the card lands, the surface brings the viewport to that block — only when the block is off screen, only once, centred, through the existing `scrollToKey` path. A card already open at mount is history, not news, and triggers no move (it must not fight open-at-the-bottom). **No standing badge, no blinking, no toast**: the scroll is the feedback, and the reader is taken to the question and answers it in place. The modal "continue or new task?" prompt this replaces is no longer needed.

**Decision 5: an execution-surface turn never splits a block.** A session's rounds arrive from two origins and both belong to the same block: Chat-originated rounds (the reference row carries `in_reply_to`, and the question row is folded in) and execution-surface rounds (`session_task` backfills the bound Chat into `TurnSurface`, but `TurnReference` is empty, so the reference row threads to no Chat row). The latter leaves no human message in the Chat transcript, so there is nothing to split on — which is also why "a block is a session" still holds.

**Scope.** Both Desktop surfaces plus the Mobile 1:1 screen take the anchor and mapping revision together (Mobile still draws the addressing card as its own row; hanging it on the block tail and revealing the block land on its own card renderer separately). No historical migration: position is computed at read time, so existing transcripts benefit too.

## Revision (2026-11-07): the reference row's obligation is decided by a grant — a forwarded Intent does not grant the initiator's Chat (D3 narrowed)

**Trigger**: Intent-forwarding investigation (2026-11-07). In a 1:1 session the user asked SSE to send PM a `create_task`. PM's turn died inside `open_round`: the Chat store refused its reference-row write with 403 `writer is not a participant of the chat session`, the human was left with `Unexpected error. See details.`, and what remained was an execution session with a 0-byte transcript and a `.rounds` entry stuck at `terminal:false`.

**The root cause is not the guard — the obligation was attached to the wrong coordinate.** D3 hangs the reference-row obligation on the **chat coordinate carried by the envelope** (`TurnSurface::from_envelope(env.source_chat_session_id)`), but that coordinate records **where the conversation came from**, not **which Chat the responder is accountable to**. A 1:1 Chat has exactly one agent participant by definition, so "forward an Intent from a session bound to a 1:1 Chat to any agent outside that Chat" fails **every time** — not a corner case, the whole channel. The guard (`chat_append`'s participant check) was right all along; what was wrong is that someone was required to perform a write it could not make.

**Decision**:

1. **Origin and obligation become two separate facts.** A delivery carries: the origin Chat (mailbox record, reply address, sweeper alert anchor, and the surface the initiator reports into) and the **surface granted to the responder**. The responder's envelope carries only the granted value; when nothing is granted it is empty and the turn has no Chat obligation by construction (`echo_chat()` / `card_target()` already collapse on an empty surface — no Runtime change).
2. **The grant is computed from membership alone**, server-side off the roster, so the sender cannot forge it: responder ∈ participants of that Chat ⇒ grant, otherwise withhold.
3. **Withheld ⇒ that turn has no Chat write obligation at all, and `has_human_participant = Some(false)`** — with no surface there is no human reachable through it. A clarification returns to the initiator as `needs_input`, and the initiator asks the human: the human's interface is the initiator, not the responder.
4. **No Chat is a third state** (cron triggers): nothing granted, and **no** assertion about human presence (`None`), so human-facing tools stay available. This state must stay distinguishable from #3, otherwise "there is no human here" and "there is no surface here" collapse into the same sentence.
5. **A human-authored delivery must grant, or refuse — never degrade silently.** On the group `@`, the 1:1 reply-to-block, and PM task dispatch, the answer's visibility *is* the responder's round block projected in that Chat (design 27 §9-8: a task response is relayed, nobody is woken; the human reads that block). If the target is not a member, the run succeeds and the answer is unreadable — precisely the black-box entry this platform has already ruled out once. So these paths now refuse before delivery: `@` naming a non-member → 400; reply-to-block resolving to a non-member → 400; PM dispatch to an agent outside the project group → `target_not_in_project_group` (a retryable failure for PM).

**Invariants**:

- The writer of a reference row is always **the agent that was granted the surface**, and that agent is necessarily a participant of the Chat — so the `chat_append` participant guard never fires along this path. The guard stays as defense in depth, not as the routine rejection route.
- **The grant and `has_human` are never configured apart**: they are two fields of one `ChatGrant` value. A turn cannot be told "a human can answer your card there" while being required to write into a surface it cannot write to — a card that cannot be written parks the turn forever, the same defect seen from the other end.

**Implementation**: `acowork-gateway` — `intent::delivery::ChatGrant` (surface + answerability as a pair), `http::intent_api::chat_grant` (the grant rule, its single producer), `intent_payload` (extracted from `deliver_inner` so the origin-vs-grant pair can be asserted side by side without a broker). All seven delivery sites state their position explicitly: `deliver_intent` (the agent-forwarding path, membership read off the roster), `deliver_response` (back to the initiator, whose membership was verified when the request was accepted), the sweeper's fallback receipt (same), `cron` (the no-Chat state), `deliver_mentions` (refuse non-members, then grant), `deliver_chat_message` (same), `dispatch_task` (same). **No Runtime or Desktop change.**

**Tests**: six gateway lib tests — one per grant state (a 1:1 forward grants nothing and asserts no human; a member keeps the surface and the origin's fact; no Chat grants nothing and asserts nothing), two on wire propagation (withheld ⇒ empty envelope Chat and `has_human_participant=false`; granted ⇒ the envelope carries that Chat), one on the mailbox (withheld, the origin still stays in the entry, so the initiator's receipt turn can still ask the human).

**Follow-ups (separate tickets, not folded in)**: (1) a **jump link** in the initiator's bubble to the responder's execution session — a shortcut, not a binding, and it must not reuse the block's execution icon, which means "bound to this Chat"; (2) error surfacing — routing/permission refusals must stop collapsing into `Unexpected error. See details.`; (3) terminal-state reconciliation for rounds (a model error mid-turn still leaves `terminal:false` residue; this revision removes its main trigger only); (4) the human entry point for the agent↔agent pair Chat is still undesigned, and this revision does not depend on it.

## Revision (2026-11-08): the wait line becomes a turn header inside the send claim (presentation layer, amends Decision 9)

**Motivation**. The two surfaces answer "I sent something, it is being worked on" asymmetrically: the execution session renders avatar + name + phase word **immediately** (the live `session_state` subscription, ADR-049), while the chat surface shows only a centered generic wait line at that moment — identity has to wait for the round's reference row and the block projection. The lag is structural: the chat content plane runs on the disk projection plus the doorbell (Decisions 3/5), and the waiting window was deliberately made "the platform's own voice" by Decision 9. But that rationale only covers half of it: the *wording* must not masquerade as agent speech, yet **identity** need not be absent — at the moment of sending, "who will this be handed to" is already an input to the delivery decision (the 1:1 peer / the `@`-mention list / the group's default responder, ADR-105), not something to be inferred from transcript shape.

**Decision 1: the wait line becomes a turn header within the claim window.** The criterion, the window, and the closing mechanism are unchanged (still Decision 9's first-person claim: it starts at the `delivered` receipt, ends at the first answering row or the deadline; `archived` sends and all-failed fan-outs arm nothing, so they show no header; a reload has no first-person claim, so no header either). Only the shape changes: the transcript tail renders the expected responder's avatar + name + one status word, reusing `ChatEventText`'s live-shimmer grammar.

**Decision 2: the naming basis is a delivery-decision input, not transcript inference.** Decision 9's "never guess the responder" ban (a group utterance fans out to several agents; naming one was a guess) narrows to: **never infer the responder from transcript shape**. The four facts available at send time — the 1:1 peer, the agent of the round a reply addresses (D6 level 1: once the server matches a round it ignores the body's `@`s), the mention list, and the default responder — are the routing's own inputs; re-routing and delivery failure are stated by server-side closing rows, and a closing row ends the claim, so a wrong name's lifetime is capped at "send → closing row" — the same window today's wait line already occupies. When the responder read fails or the identity cannot be resolved (directory not ready), the header degrades to the generic centered line; a nameless avatar is never rendered. An addressed row that sits outside this surface's loaded window is treated the same way — unresolved is not the same as absent, and substituting the mention list would name an agent that never receives the send.

**Decision 3: the status word reuses `getProcessingPhase()` — no new chat-side enum** (ADR-049's single source of truth). Inside the claim window, before the round's coordinates land, the only honest word is a generic "working" — the claim is a fact about the window existing, not about a phase. Once the coordinates land and the execution session is resident locally, the header may subscribe to its live status and show the real phase word under the same rules as the block header (the live word wins, the read-derived word is the fallback, presentation-layer add-on only: never persisted, never in context, never in unread counts — Decision 9's item 4 applies verbatim); cross-machine rounds keep the generic word, which is the normal case, not an error.

**Decision 4: "overwrite" = the claim ending — no new folding logic.** When the first answering row (the round's reference row / an agent message / a receipt) lands, the claim closes, the header disappears with the window snapshot, and the round's content is taken over by `ChatExecutionBlock`'s own avatar header (or the agent bubble's header) at the same avatar anchor (the existing `avatarAnchor` machinery) — visually continuous, no jump. A multi-target fan-out renders ONE stacked header (avatar stack + name list): one send is one fact, not N headers.

**Amendment (2026-11-08b, the role line)**: the turn header carries the agent's `role` on a line **under** the name (the same registry meta field, on the same tier, as `ChatExecutionBlock`'s header and a regular agent message header), so its shape is avatar + name + role + status word. The reason is Decision 4's takeover invariant: the block header renders name + role, so a claim window showing only the name would have to *insert* a line under it at handover and shift the whole column; with the role already in place the takeover removes the status word and moves nothing. A multi-target fan-out renders **no** role line — a joined list of roles names no single responder, and the avatar stack already says "several".

**Amendment (2026-11-08c, the status word's position)**: the turn header's status word moves **out** of the identity column (the name + role one) into the block's **content column** — the row that starts with the same 40px spacer as the block body, i.e. the column where `ChatExecutionBlock`'s "Explored" row sits. The earlier shape made the word the identity column's third line, which broke Decision 4 twice: the `items-center` row grew with that column, lifting the name and role off the avatar's axis; and at handover the word would have had to jump sideways into the content column — exactly the re-layout "the takeover removes the status word and moves nothing" forbids. The identity row now wears the block header's own classes (`mb-2 mt-1 flex items-center gap-2`), so avatar / name / role geometry is identical before and after the takeover, and the only thing replaced is that one line in the content column.

**Invariants kept**: terminal closings (`aborted` / `failed` / `timeout` / `waiting`) remain centered platform lines, never avatar-wrapped — a stop is not the agent speaking; hole-class messages (`block.notFound` and friends) likewise. Decision 9's three invariants (centered terminal rows, live-as-presentation-only, unreachable ≠ running) hold unchanged.

**Scope**. Both Desktop surfaces (`AgentChatView`, `GroupChatPanel`) and Mobile's 1:1 surface switch in step; a shared component plus one resolution function (`resolveExpectedResponders`) are added, and the claim metadata (the expected responder instance ids) rides `armTurn` at send time and clears with the claim. Pure presentation: no new network endpoint, no proto field, no storage write. Design detail and delivery phases: design 33 (`docs/design/en/33-chat-turn-header.md`).
