# ADR-100: Chat Event Log — Remove the Execution Status Card, Land In-flight Turns as Point-in-Time Event Rows

- **Number**: ADR-100
- **Status**: Accepted (Rev. 5, 2026-10-24: with ADR-099's rotation deletion the `opened_new` value space collapses — see D11; Rev. 4, 2026-10-23: the execution view's composer sends through the chat entry, with a direct pin that skips the router — see D12; Rev. 3: the routing reaction row is persisted and the avatar invariant is established — see D11; Rev. 2: intermediate state is no longer persisted — see D10)
- **Date**: 2026-10-22 (Rev. 2 / Rev. 3 / Rev. 4: 2026-10-23; Rev. 5: 2026-10-24)
- **Deciders**: ACowork Architecture Group
- **Related**: Design 27 (Intent Messaging and Group Chat §5.5.4 / §5.5.5 / §6), ADR-099 (Chat Router, D3 routing-time delivery anchor), ADR-086 (Mobile Multi-Session), ADR-049 (Session Status Substates), ADR-096 (No Full Session Reads), ADR-098 (Unified Standard Group Model)

## Summary

v2.1 (contemporary with ADR-099) layered a **live status-mirror card** (`ExecSessionStatusCard`) on top of the chat event log: its visual state was a read-time projection of the execution session's `session_state`, used to express "this message is being handled / the run is at step N". This ADR **reverts that card** and returns chat to a **pure point-in-time event log** — the in-flight turn is expressed by fixed `turn_dispatched` / `turn_started` event rows, "still running" is expressed by the next round's own started row, and execution-phase detail is reached through a "view run" drill on the event row rather than mirrored in chat. (How those rows are *presented* is D7: a turn pointer renders as the agent's attributed reaction, not a centered system notice.)

Root cause: chat is an append-only durable event log; the live card was a **second truth** layered on it (fed from the execution session's state machine), and the two truths can never stay aligned, producing two classes of user-visible defect.

> **Revision Rev. 2 (2026-10-23)**: D2 / D3 / D6 / D7 / D8 landed "dispatched / round opened" as durable rows, and that still misfit the medium. For a **transcript**, "your message reached the agent" and "this round started" carry nothing a reader wants, yet they filled every history with status lines; the fact that actually needs explaining — "why did this message get no answer" — is expressed by the terminal row. So intermediate state is **no longer persisted**: the Runtime stops writing `turn_dispatched` / `turn_started` / `router_fallback`, the live wait feedback becomes a single aggregated line **derived** by the frontend from "the newest human message has no terminal answer yet", legacy rows are hidden at render time, and the `aborted` / `failed` / `timeout` / `waiting` terminals stay — as centered status lines. See D10.

> **Revision Rev. 3 (2026-10-23)**: Rev. 2 was right to drive **progress** out of history, but it also removed D8's **conversational feedback** — after the user sends, the chat shows only the derived centered wait line ("{{name}} is working on it…"), and between the routing verdict and the final answer (minutes or hours) no agent message appears at all. A chat's feel of exchange comes from **call and response**: a human message must be followed by an agent avatar + name + bubble, whatever its content. So **one** durable reaction row returns — `turn_routed`, written the moment the routing verdict is resolved, reading "Starting a new task: {task}" or "Continuing the earlier task: {task}". It is not progress; it answers "where did my message go", a fact of the conversation that a reader months later also needs. Alongside it, the avatar invariant is established: an empty terminal row paints as a centered status line and must NOT fold the avatar off the agent bubble that follows it. Everything else in Rev. 2 (no progress rows, the derived wait line) stands. See D11.

> **Revision Rev. 4 (2026-10-23)**: D9 echoes a chat-bound execution session's **output** into chat, but that turn's **human message itself** still lives only in the execution session's JSONL — so chat renders a half turn: an answer with no question. The cheapest fix (the Runtime appending a row **as** the user) is rejected: the writer's identity must be the initiator's. Rev. 4 therefore replaces the entry instead of backfilling it — **the execution view's composer sends through the chat entry** (`POST /api/intents/chat-message`) carrying `for_execution_session` to name its own session. A message arriving with that pin **skips the Chat Router** and is delivered into the named session as a `SessionMessage::ChatMessage` (never an `Intent`), joining the same handling the execution surface always had — so skills, attachments and the native JSONL user row all survive with zero capability regression. A stale id costs one routing hop, never the message. See D12.

> **Revision Rev. 5 (2026-10-24)**: ADR-099's 2026-10-24 revision deletes the physical rotation of execution sessions, so `chat_dispatch` / `route_intent_session` collapse from a three-element to a **two-element** return (`(session_id, opened_new)`). D11's `opened_new` keeps its meaning — it is still the point-in-time fact of "did this turn physically create a session" — only its value space no longer contains a rotation branch: a reuse (including `dispatch(existing)`, switching to another live session) reports `false`, and only a physical create reports `true`. The two `turn_mode` states, the durable write and the rendering contract are unchanged.

## Background

### 1. The structural conflict of two truths

- **Visibility gap (problem 1)**: once a message is routed into a busy execution session and starts a new round, the chat-side early `turn_started` pointer was deliberately hidden by the frontend (`notice_type === "turn_started" return null` in `AgentChatView` / `GroupChatPanel`), so the window between dispatch and reply showed no feedback at all.
- **Card fights the truth (problem 2)**: the card mirrored live session status. When the user stopped the current round → `mark_turn_aborted` marked it aborted → the card vanished instantly; but a force-queued pending message had already started a new round and execute was not idle. The card's "finished" contradicted the real "still running".

### 2. The three paths are already isomorphic

Single chat (1:1), a human group-chat @, and a PM task dispatch were verified to take the **exact same routing path** (`IntentMessage` → `route_intent_inbound` / `route_intent_legacy` → chat_dispatch creating/reusing an execute session); the backend already wrote an early pointer to the corresponding chat session id at routing time, and the frontend was merely hiding it via `return null`. Therefore "make the pointer a visible event row" naturally fixes all three paths at once, with **zero new backend writes**.

## Decision

### D1 — Chat returns to a pure event log; delete the live status-mirror card

Delete `ExecSessionStatusCard` (and its read-time projections on both clients: `projectLiveTurn` / `projectInFlight` / `live` / `inFlight`). Chat maintains no mirror of the execution session's live state. Rationale: the live mirror and the durable event log are two truths that cannot align; deleting the card makes both defect classes vanish at once, and "still running" is a fact that the next round's `turn_started` row already expresses, so no persistent-state widget is needed.

### D2 — The in-flight turn lands a minimal set of two pointer rows, both written by the Runtime

- **Dispatch row `turn_dispatched`**: at the moment the Runtime accepts a `user_message` (or a PM `request`), resolves an execution session, and writes the routing, it appends a `system_notice` through the single chat write entry point with `notice_type = turn_dispatched`, carrying `in_reply_to` + `agent_session_id`, idempotency id prefix `td:{message_id}`. This is the ADR-099 D3 "early `turn_started` pointer written at delivery time" **renamed** (two sites changed together: `route_intent_legacy` and the chat_router drain in `runner.rs`).
- **Started row `turn_started`**: written when the round actually dequeues and starts (`session_task.rs`), keeping its existing id `ts:{message_id}`, with the meaning narrowed to "round started".
- **Coexist, not mutually exclusive**: the same `message_id` yields two ids because the prefixes differ (`td:` / `ts:`), and the store dedupes on the exact `message_id`; when a force-queued pending starts a new round, that round's `turn_started` truthfully shows "still running".
- **Terminal outcome reuses `agent_message`** (completed / failed / aborted / waiting); no new row.

The writer is still the Runtime, same origin as ADR-099 D3; no second write entry point is added, and the Gateway fs redline is not touched (ADR-009 §5).

### D3 — Minimal event granularity; execution-phase detail never enters chat

No fourth row type is added to further split "queued vs started immediately". `turn_dispatched` (written at routing) covers the immediate visibility for problem 1; `turn_started` (written at round start) covers "still running / a new round began". Tool execution, streaming output, and todo progress **do not enter chat** (neither as event rows nor in the router context Block B). The server-side read-only pending-queue mirror inside the execution view (Design 27 §5.5.5) is kept untouched — it is an execution-side capability unrelated to the chat-side live card.

### D4 — A "view run" drill, not a status mirror

Every event row carrying an `agent_session_id` (the dispatch row, the started row, and any `agent_message` that resolves an execution session) is given a discrete drill-down affordance (brain glyph + "view run") that best-effort opens the physical execution session that actually ran the turn (a definitive 404 existence probe → toast, no navigation). The chat surface neither reads nor holds the execution session's live state.

### D5 — Interaction cards stay answerable in place; the three paths share one renderer

`interaction_request` (ask_question / permission approval) remains the §5.5.4 decision card, answerable in place in the chat stream; the answer rides the chat channel → Gateway `resolve_card_answer` continues the original turn. The desktop extracts two shared components, `ChatNoticeEventRow` (event row) and `InlineInteractionCard` (in-place card), reused by 1:1, group chat, and PM dispatch as one grammar; the mobile client collapses them to a one-line text plus a "view run" drill, with interaction items still in a bottom sheet.

### D6 — Immediate send-side feedback moves to a frontend transient placeholder

The dispatch row appears one round trip after the user presses send, absorbed by a **non-persisted frontend transient "sending" placeholder**; once `turn_dispatched` is stored it is replaced by the durable event row. The placeholder is not persisted, so if the durable row never landed, the placeholder disappearing after a refresh is correct. This does not contradict D1's removal of the live card — the transient placeholder is pure frontend render state, not a second persisted truth.

### D7 — Event-row presentation: a turn pointer is the agent's attributed reaction, not a centered system notice

A chat is a conversation: after the user says something, the agent must answer. `turn_dispatched` / `turn_started` are not channel-level system notices (that category is impersonal facts like `router_fallback`) — they are **the executing agent's own non-textual reaction to the turn** (the equivalent of a human replying "sure, let me look into it"). So the presentation is:

- **Attributed to the agent**: a turn pointer renders on the agent's side, with its avatar + name (shown in both 1:1 and group; in a group it is essential, otherwise with several agents you cannot tell who is handling the turn). The attribution data is already on the durable row (`from` = the executing agent); the render layer had simply been discarding it as a centered system line.
- **One reaction per turn (collapse)**: a turn's `turn_dispatched` + `turn_started` for the same `in_reply_to` collapse at render time into **one row** reflecting the most-advanced pointer (started → "on it", dispatch-only → "queued"). This is a read-time projection over the durable stream, **not a live mirror**; the JSONL keeps both rows, and dedup / unread / context / the optimistic-title seed still read the full stream.
- **One bubble per turn (fold into the reply)**: when the collapsed reaction row is **adjacent** to the terminal `agent_message` of the same turn (same `in_reply_to` + same `from` + same or one-missing `agent_session_id`), it no longer occupies its own row but folds into the **top of that reply bubble as a one-line caption** — one turn keeps a single avatar / name / "view run", removing the "reaction row + reply bubble" duplicate identity and drill. While the turn is still running (the reply has not landed yet) or a card breaks the adjacency, the reaction stays standalone as in-progress feedback. Also a read-time projection (`groupTurnReactions`); the durable rows are untouched and both desktop surfaces plus mobile follow the same pairing contract.
- **Agent-voice wording**: the text moves from system jargon ("Dispatched to execution" / "Started running") to the agent's voice ("Got it — queued" / "On it").
- **Impersonal receipts stay centered**: `router_fallback` and generic body/status remain a quiet centered system line — they are routing/channel facts, not some agent speaking.
- **Presentation only**: this decision changes Desktop / Mobile rendering and i18n; it does not touch the backend write entry point or the durable semantics (D2 / D3 unchanged).

### D8 — The `turn_started` reaction splits into "new task / continue task", naming the execution session

D7's reaction was the single "On it", so every turn read the same and the user could not tell from chat whether the agent was *starting a new task* or *continuing an earlier one*. This decision further splits the `turn_started` reaction into two voices, driven by the **backend's authoritative routing-time decision** stamped into durable meta — the frontend only renders, it never infers:

- **`turn_mode` meta (a new durable field)**: `chat_dispatch` and `route_intent_session` gain an `opened_new` return value (Rev. 5: after the rotation deletion the return is the pair `(session_id, opened_new)`) — a reuse (already-mapped / switching to a live session) reports `false` (the same task continues); only a fresh create reports `true` (`Target::New` is always `true`). The value rides the routing anchor into `SessionMessage::Intent.opened_new`, and `dispatch_pointer_meta` / `started_pointer_meta` stamp it as `"turn_mode": "new" | "continue"`, **on both the `td:` and the `ts:` row** (the collapsed row shown is usually `ts:`, so both carry it to avoid losing the signal). It is a point-in-time fact fixed at routing, never re-derived on read.
- **Two voices**: a `turn_started` with `turn_mode=new` renders `chatView.notice.turnStartedNew` ("Starting a new task: {name}"); `turn_mode=continue` renders `chatView.notice.turnStartedContinue` ("Continuing the earlier task: {name}"). `turn_dispatched` stays the neutral "Got it — queued" and never splits.
- **Task-name resolution (presentation layer, durable rows untouched)**: prefer the execution session's own title (Desktop `useSessionTitle` reads the live overlay / snapshot; Mobile reads the agent store's session list, treating the "新会话" placeholder as empty); when the title is empty (a brand-new run not yet named) fall back to the triggering message body (the parent's `in_reply_to → body` index, clipped by `truncateTaskName`). When neither resolves, fall back to the original single `chatView.notice.turnStarted` — never render a nameless "...: (empty)" fragment. The `ViewRunButton` tooltip shows the same task name.
- **Scope and compatibility**: both desktop surfaces plus the mobile reaction row; all five locales gain `turnStartedNew` / `turnStartedContinue`. What is added is **one durable meta field**, backward compatible — an old `turn_started` row without `turn_mode` simply renders the single line, no migration. The writers remain the two builders and the two dispatch sites; no new write entry point, the Gateway fs redline stays untouched (ADR-009 §5).

### D9 — An execution session started from a chat must write its locally-composed continuation turns back to that chat

An execution session started from a chat **belongs to** that chat permanently (`set_chat_binding` already persists `chat_session_id` into the session meta). But write-back was implemented **per turn, decided by the chat request that triggered it**: a chat-routed turn carries "owes the chat a write-back" (`chat_writeback`) and posts it at turn end; a turn the user **composes directly in the execution session's composer** (typically: stop a chat turn by hand, then send a new message there to continue) has no request context, so `chat_writeback=None` and its output is never posted back — the chat stops at `aborted`, and every continuation plus the final completion stay invisible.

This decision widens the write-back basis from "the message that triggered it" to "the session's ownership": as long as an execution session is bound to a chat, its **local turns'** final output must also write back to that chat.

- **Trigger**: when a `SessionMessage::ChatMessage` turn (the execution composer's sole entry) ends, if the session's `chat_session_id` is non-empty and the output is non-empty, append a **standalone `agent_message`** to that chat.
- **Row shape**: no request to answer and no thread to hang under, so `in_reply_to` is empty (standalone); `meta.message_id = "exec:{local turn message_id}"` (the idempotency key — a redelivered turn cannot double, and it never collides with the `td:` / `ts:` pointer ids); `meta.sender_session_id` = the execution session (the renderer drills on it, so no frontend logic is new); `status="completed"`; `to` empty (broadcast — every group member sees it / the 1:1 peer). The body uses the same `truncate_response_body` cap as §7.1.
- **No double-write**: a chat-routed turn still writes back through the original request/response path (the Intent arm); a local turn writes back through this decision (the ChatMessage arm). The two arms are disjoint, so one turn lands exactly one row.
- **Boundary widened**: the `POST /api/intents/chat-append` kind whitelist grows from `interaction_request | system_notice` to the three, adding `agent_message` (the writer identity is still node-token-verified, `from` must be a session participant, `meta.message_id` is still required). The store's `IntentMeta` already has every field; no storage change.
- **Best-effort**: a failed echo only logs and never affects the turn; what is lost is a surface row, never the conversation.
- **Debug replay adds no second row**: the DevMode resume / step replay (ADR-013) continues the *same* paused turn rather than a new user turn, and `exec:{message_id}` is idempotent per turn — so a replay does not append a second row; the execution surface stays the source of truth for that debug flow.
- **A stopped local turn writes no row** (superseded by D10): only a final output is echoed. When a local turn is stopped, the execution surface shows the interruption but chat gets no extra row; the chat's "interrupted" line still comes only from a chat-routed turn's `aborted` write-back (§7.1), so repeated local stops do not accumulate interruption notices in chat.

### D10 — Revision (Rev. 2): intermediate state is not persisted; history keeps only terminals

Every decision above rested on one premise: an in-flight turn must land as durable rows. Measured against real transcripts that premise is half wrong: **live feedback needs immediacy, while reading history needs no progress at all**. "The message was dispatched" and "the round opened" are execution-side runtime facts, worth zero to someone scrolling a conversation months later; persisting them mixes a progress log into a conversation log. This revision therefore separates the two cleanly:

1. **Stop writing intermediate state.** The Runtime no longer writes `turn_dispatched` / `turn_started` / `router_fallback`, and the `dispatch_pointer_meta` / `started_pointer_meta` builders are removed together with their three write sites (the chat_router drain dispatch, the `route_intent_legacy` dispatch, and the `session_task` round open). The `turn_mode` durable meta (D8) is retired with them and no longer produced. The store still deserializes legacy rows (the fields remain), it just never adds new ones.
2. **Hide legacy rows at render time.** Existing `turn_dispatched` / `turn_started` / `router_fallback` rows are neither migrated nor deleted, but neither Desktop surface nor Mobile renders them (`RETIRED_NOTICES` in `ChatNoticeEventRow`). A refresh, a new device, or an old backup can never paint a status line back onto the screen. `ChatNoticeEventRow` is then left with genuine channel receipts only (`budget_exhausted` / `delivery_failed` / `truncated` / `unavailable`, …).
3. **The live wait line is derived by the frontend (never persisted).** The test is the only durable evidence there is: **the newest `user_message` that actually asked an agent something has no terminal answer yet**. "Did this human row really wake an agent" is itself a fact on the row, not a guess: a row written by `/api/intents/chat-message` carries in `to` the agent it was delivered to (1:1, a card answer and a pinned execution turn all ride it), and the §5.3.1 group fan-out writes ONE broadcast row (`to` empty) naming the mentioned agents in `meta.mentions`; everything else — a `user_user` DM, an un-@'d group remark — goes through the archive-only chat write entry, which stores an empty `to` and no mentions and wakes nobody. The wait line asserts "an agent is working", so **a human row that woke nobody neither opens the wait nor counts as the "newer human message" that supersedes the previous turn** (an aside typed into a group does not cancel the task still running there); conversely a chat with no Agent participant at all (a DM, a humans-only group) never shows the line, not even inside `sending` — nobody is coming back with an answer. `pendingTurn(rows, sending, closedCards, agentReachable)` returns false outright when `agentReachable=false`, short-circuits to true while the HTTP send is in flight, and otherwise walks back to the newest row that opens an agent turn and stops waiting when any of these appears after it: a terminal `agent_message` answering it (`in_reply_to` match), an OPEN `interaction_request` (the ball is with the human), or a newer human message that opens a turn of its own. With an agent name it renders `{{name}} is working on it…` (shimmering), else the generic line; it does not distinguish queued / round-open / tool-running, adds no MQTT channel and changes no session-list API. It is suppressed when a locate has parked the window mid-history (newer pages exist).
4. **Terminals stay; an empty terminal turns centered.** `aborted` / `failed` / `timeout` / `waiting` `agent_message` rows are still written and kept (they answer "why was there no reply", which is exactly what history needs). An empty-body terminal (no attachments) no longer paints as an agent bubble — a status word is not something the agent said — but as a centered status line (`aborted` neutral, `failed` / `timeout` red) that keeps the "view run" drill; a terminal with a body remains an ordinary bubble.
5. **A stopped local turn lands an `aborted` terminal (superseding D9's last bullet).** When a chat-bound execution session's local turn is stopped it is no longer silent: an empty-body `agent_message` (`exec:{turn_id}` idempotent, `status="aborted"`, `sender_session_id`) explains in chat why the message went unanswered. Repeated stops dedupe on the idempotency key and never accumulate notices.
6. **Presentation and scope.** Desktop `AgentChatView` / `GroupChatPanel` and Mobile `AgentChatScreen` share one rule set and the same centered status line (Mobile carries its own shimmer); all five locales gain `pendingTurn` / `pendingTurnGeneric` / `interrupted` / `failed` / `timeout` / `waiting` / `noAnswer` and drop `emptyReply` plus the four old notice keys (`turnDispatched` / `turnStarted` / `turnStartedNew` / `turnStartedContinue`); the `routerFallback` key survives only as a fallback for old receipts and is never painted.

**Why not "persist but hide"?** That trades in-process state for permanent garbage: once written it must be considered by truncation, compaction, context filtering, unread counts, export and backup, while carrying no conversational value; and live feedback would still need a frontend signal to appear immediately. Not persisting removes the two-sided sync problem at the root.

**Relation to D1.** D1 removed the chat-side read-time **mirror** of execution state; D10 also removes the chat-side **write** of execution progress. Together they complete "chat = conversation history": history records what was said and the fact that something went unanswered; progress exists only at runtime, in the live window.

### D11 — Revision (Rev. 3): the routing reaction row `turn_routed` is persisted, and the avatar invariant is established

Rev. 2 was right to drive **progress** out of history, but it also cancelled D8's **conversational feedback**, leaving a more basic hole: after the user sends, the chat shows only the derived centered wait line ("{{name}} is working on it…"), and between the routing verdict and the final answer (tens of minutes to hours) there is not one agent message. A chat's feel of exchange comes from **call and response** — a human bubble must be followed by an agent avatar + name + bubble; without that immediate reaction the user cannot tell the message was received, let alone which task it went to (the incident that surfaced this shipped the same day the revision did: a fresh-topic message was degraded-routed into an unrelated historical session while the chat showed nothing but "working on it", no follow-up at all).

1. **One durable reaction row returns, and only one.** After the routing target resolves and the intent is delivered, the Runtime appends one `system_notice` whose meta is built by the shared builder `turn_routed_meta`: `message_id = "tr:{request_id}"` (idempotent per trigger row — a redelivered envelope adds no second row), `in_reply_to = {request_id}` (threaded under the human message that triggered it — which is exactly what "immediately after the user message" means), `agent_session_id` (drillable), `turn_mode = new | continue` (a one-time routing-time fact: only a physical creation is `new`; a reuse of an existing session (in-place appends included) is `continue` — the same logical task carries on), and `notice_type = "turn_routed"`. The body stays empty: the wording belongs to the UI language and is rendered from i18n — the user's language is never baked into durable data. Two write sites: the chat_router drain's `dispatch` success arm (covering 1:1 / group @ / every pre-degradation routed turn) and `route_intent_legacy` for turns that owe their chat a write-back (covering the router-off human turn and the PM dispatch). Against Rev. 2's three removed write sites, exactly one remains.
2. **It is not progress — it is a fact of the conversation.** "Your message was dispatched" is zero-information progress for a reader; "**which task handled this message — a new one, or the continuation of an earlier one**" is a fact of the conversation itself, needed months later too. This is the boundary between Rev. 2's "history records no progress" and conversational value, and `turn_routed` falls on the value side. The derived wait line (D10.3) is NOT withdrawn: after the reaction lands the run is still in flight, so the live line keeps covering it until the terminal — different jobs (one is the agent's reply, the other is runtime state).
3. **Rendered as an attributed agent bubble, never centered.** Desktop `AgentChatView` / `GroupChatPanel` and Mobile `AgentChatScreen` fold the `turn_routed` row into the ordinary agent-bubble path: avatar + name + bubble, reading `Starting a new task: {{task}}` / `Continuing the earlier task: {{task}}` (five-locale keys `chatView.notice.turnRoutedNew` / `turnRoutedContinue`). The task is named by its execution-session title, falling back to the (truncated) trigger body while no title exists — the same naming rule as D8. `RETIRED_NOTICES` is unchanged: `turn_dispatched` / `turn_started` / `router_fallback` still never render.
4. **The avatar invariant.** Every row that actually renders as an agent bubble carries the avatar + name attribution, and the "fold the header because the row above was already a bubble" test counts only rows that **rendered** as bubbles: an empty terminal row is a centered status line (D10.4), not a bubble, and must not fold the avatar off the reply that follows it; the `turn_routed` reaction and the turn's real reply each wear their own header (they may be hours apart — the reaction "catches" the message, the reply answers it; they are not one utterance continued). After Rev. 2 the `AgentChatView` `showHeader` test keyed on `kind === "agent_message"` alone, counting the centered terminal as a bubble and stripping the avatar off the reply that followed — this item pins the test to "the previous row **rendered** as a bubble". The execution-session view follows the same rule: the agent message right after a user message always carries the avatar.

**Why not a durable row that carries the wording.** Baking "Starting a new task: xxx" into the body burns the UI language into durable data and forces a wrong-or-backfilled task name when the title arrives late (append-only forbids the backfill), while the two durable facts `turn_mode` + trigger body already let the renderer compose the correct copy at any time.

**Relation to D10.** D10 removed **progress** from persistence (dispatch / round-open / the fallback receipt); D11 restores the **conversational feedback** (where the message went). The former is zero-value to a reader; the latter is not — the test is always "would a reader months later want to know this".

### D12 — Revision (Rev. 4): the execution view's composer sends through the chat entry, and a direct pin skips the router

D9 makes a chat-bound execution session write its **local turn's output** back into chat, yet the **human message** of that same turn still exists only in the execution session's JSONL — so the chat reads as half a turn, "an answer with no question", and someone scrolling months later cannot see what words started the task. The cheapest way to close that gap is to have the Runtime append a row **as the user**, and that route is rejected: the identity at a write entry must be the initiator's identity; writing on someone's behalf turns "who said this" into an implementation detail. So this decision changes the entry itself — **what a human types in the execution view enters through chat**.

1. **The entry changes; the destination does not.** When an execution session is bound to a chat (`SessionInfo.chat_session_id`), its composer sends through `POST /api/intents/chat-message` carrying `for_execution_session = that execution session`. The Gateway appends one `user_message` under the caller's own identity (this turn's head); the Runtime, on receiving it, **skips the Chat Router** and delivers straight to the named session (this turn's tail). "Who answers this" is settled by which view the human was typing in — no routing LLM call is needed to rediscover a fact that is already decided. When the bound chat is a project group (which is exactly what a PM task's session is bound to, ADR-099), the group holds more than one agent and no target can be derived from the chat alone, so the request also carries `pinned_agent`, naming the instance that owns the execution session. It is a **checked claim, not a trust**: the instance must be an Agent participant of this very chat, or the send is a 403 and no row is written — this turn's answer gets filed in this chat, so the named session has to belong to it. A group send with no pin still goes to §5.3's archive entry; this decision did not open that door.
2. **Direct delivery carries a `SessionMessage::ChatMessage`, not a `SessionMessage::Intent`.** Intent is the agent↔agent protocol shape and has none of the three arms `active_skill` / `attached_items` / `content_parts`; delivering into it would shave a slice off what the execution composer can do. Delivering a ChatMessage makes a pinned turn **equivalent item-for-item** to the same send made on the execution surface: a slash skill is still resolved by the Runtime against the `SkillRegistry` (a command is never trusted from the client), attachments still land in that session's `files/` per the ADR-046 union type, and the JSONL still records a native user row. The zero capability regression is a consequence of this choice, not an extra compatibility layer on top of it.
3. **The pin is a hint, never a gate.** If the target session is not loaded, the Runtime clears the hint and falls through to the ordinary route — the price is one routing call, never the message. Being loaded in this instance is not yet ownership: one agent instance serves many chats, and session ids travel on rows other people can read (a group's `meta.agent_session_id` is visible to every member), so the receiving Runtime also verifies that the chat the pinned session is bound to **equals** the chat this send came from, and a mismatch clears the hint the same way. Without that check, anyone could inject text, a per-turn skill and node-local attachment paths into somebody else's running task — that task's answer would be written under the agent's identity into the victim's chat, while the attacker's own chat kept the head of a turn that never ran there. A targeted send with no content at all (no text, no attachment, no content_parts) is settled as complete on the spot: it neither wakes a session only to drop the message with a warning downstream, nor burns a routing call for nothing. The chat row the Gateway already wrote still records truthfully what the human sent.
4. **One client-minted row id aligns three places.** The execution view mints the `message_id` for the bubble it paints optimistically, and that same id becomes both the chat row (validated by `is_valid_row_id`: 1–64 characters of `[A-Za-z0-9_-]`, anything else is a 400 — no silent normalization) and that session's JSONL row. So **the optimistic insert, the rollback and the reconciliation all stay untouched**, and the two send paths converge on one id by construction.
5. **The write-back is threaded, and the exchange reads as one turn.** `exec_echo_meta` gains a fourth parameter `trigger_message_id`: a pinned turn's terminal `agent_message` carries `in_reply_to = that chat row id`. D10.3's derived wait line then sees the message as answered and disappears, and chat reads the exchange as one complete turn — what was asked here, plus the answer it brought back. A non-pinned turn (the execution surface's own write path, and chat's own composer) still writes a standalone `exec:` row with no `in_reply_to`: it owes no visible row an answer.
6. **Attachments are not carried across systems.** Bytes never ride MQTT (the `/api/intents/chat-attachments/…` streaming endpoint exists precisely for that discipline), and a node-local path necessarily 5xxes the moment Gateway and Node sit on different hosts (the ADR-009 §5 red line). So the chat row carries **display names** in `meta.exec_attachments` and nothing else — the upload arm's `filename`, the workspace arm's `name`, a basename only when an item sent nothing but its path — never a documentId, a path, or an openable reference; the execution view remains the only place an attachment can actually be opened. That is not a compromise: a reference in chat that cannot be opened is worse than no reference. Two hard constraints follow in the implementation: the chat store's `IntentMeta` is a strongly typed struct, and **serde silently drops any meta key it has not declared**, so this field must be declared at the storage layer or the projection writes into a row that never persists it; and the store's "a `user_message` needs content" rule counts those labels as content — a file with no words is a legitimate turn on the execution surface, and refusing it would drop the head row of a turn the surface accepted. Both clients paint the label as a **muted, non-interactive pill** (visually distinct from a downloadable chat attachment chip), and the label itself counts as content there, so the head never degrades into a blank bubble.
7. **`command` and `attached_items` are honored only alongside a pin.** Without a pin the turn is consumed as an Intent, where neither arm exists, so accepting them would show the chat a chip the agent never received. Without a pin they are emptied rather than rejected — the human's text still arrives verbatim — and with a pin they are bounded: `command` ≤ 128 characters (a skill *name*, not instructions), `attached_items` ≤ 32 entries and ≤ 32 KB serialized.
8. **The clients trust only server-side facts.** Desktop and Mobile branch the execution composer on whether `chat_session_id` holds a value; with no binding, or in local mode (no account — the chat channel is an identity channel and forcing it would only produce a 401), they keep the original `POST /sessions/{sid}/messages`. The binding is read only from the session row the Runtime exposes; the frontend never invents, caches, or rewrites it.
9. **Every way a turn can end owes a terminal row.** Now that the head is written every time, the tail cannot be written only when the model had something to say: a finished answer, a stopped turn, an attachment that could not be read and an agent loop that returned an error all thread the same `trigger` into one `agent_message`, with `status` = `completed` / `aborted` / `failed`; a `failed` body is the human-readable line alone — detail and error type never enter a transcript. Otherwise the round reads "in progress" in chat from that moment on while the truth lives only in the execution view. D9's original "an ordinary empty answer leaves no row" survives on the non-pinned path only, which has no chat question to close.
10. **The terminal row also closes the mailbox request.** When the Gateway delivers this `user_message` it records an unanswered request in the mailbox (that is what §7.1's timeout fallback keys on), and a pinned turn has no Intent write-back to close it; so `chat-append`, on `kind=agent_message` with a non-empty `meta.in_reply_to`, calls `mark_answered(in_reply_to)` once the row is durable — the same ordering as the Intent write-back, answer first, close second. Without this step a round that was answered perfectly still gets a `fallback-{message_id}` `failed` receipt appended to the same chat after the response deadline (3600 s by default, or the 60 s liveness grace once the responder is offline), pointing at a head row that was answered long ago: the human sees "I asked, it answered, and an hour later it said it never got an answer". Decision cards and resolution notices ride the same relay with their own `in_reply_to` (an execution-side request id, or their own card) — those are not chat requests and close nothing.

**Why not "append the chat row once the execution turn finishes" instead.** That is still writing on someone's behalf, with the forgery merely moved later: the writer would be the Runtime, the identity would be the user, and it adds a sequencing race against the delivery outcome. Going through the chat entry reuses a contract that already exists — the row is durable before delivery is attempted (§5.1) — and introduces no new writer at all.

**Relation to D9.** D9 supplies the **tail** (a local turn's output must echo back); D12 supplies the **head** (that turn's human message must be present). D9's write-back contract is not changed: a non-pinned local turn still writes a standalone `exec:` row, and a pinned one merely carries one extra `in_reply_to`.

**Relation to D10 / D11.** D10 removed durable progress rows and D11 restored one conversational reaction row; D12 introduces **no** new row type — it relocates an already-existing `user_message` from the execution surface into chat. A pinned turn writes no `turn_routed` either: it was never routed, so there is no destination to announce, and the human is watching it run.

## Acceptance Criteria

> Items 1–8 are Rev. 1 acceptance and 9–13 Rev. 2 acceptance (both kept for the record); the current criteria are 9–17 below (14–16 are new in Rev. 3 and 17 is new in Rev. 4, both coexisting with 9–13 — Rev. 3 restores only the `turn_routed` reaction row and Rev. 4 introduces no row type at all, so neither undoes Rev. 2's no-progress-persistence rule).

1. **Problem 1 gone**: between sending and the reply being stored, chat shows at least one visible `turn_dispatched` event row (identical across the 1:1 / group @ / PM-dispatch paths).
2. **Problem 2 gone**: after stopping the current round, when a force-queued pending starts a new round, chat shows that new round's `turn_started` event row truthfully expressing "still running", with no stateless persistent card fighting the truth.
3. **Dual-write dedup**: `turn_dispatched` (id `td:`) and `turn_started` (id `ts:`) coexist without being mutually exclusive. The two pointer rows' `meta` are built by shared builders — `dispatch_pointer_meta` (called by both dispatch write sites: the chat_router drain and `route_intent_legacy`) and `started_pointer_meta` (round open). A unit test locks both builders' `td:`/`turn_dispatched` and `ts:`/`turn_started` literals (reverting either fails the test), and a store-level test verifies the two ids each keep one row and are each idempotent. All three paths (1:1 / group @ via the chat_router drain, PM dispatch via `route_intent_legacy`) land through these two builders, so they share one dedup contract — no per-path integration test is needed.
4. **No live-projection residue**: neither client store still has `projectLiveTurn` / `projectInFlight` / `live` / `inFlight`; only the card-receipt-needed `closedCardIds` / `humanAnsweredCardIds` remain.
5. **Drill works**: the "view run" drill on event rows and `agent_message` works naturally for PM task sessions (the `agent_session_id` is in the pointer meta, bound to the group per ADR-099 D5).
6. **Attributed presentation (D7)**: a turn pointer renders as an agent-side reaction with avatar / name in both 1:1 and group; a turn's dispatch + start collapse to one row (`hideSupersededDispatchIds` read-time projection, same contract on Desktop / Mobile); once the adjacent reply lands the reaction folds into that bubble as a caption and the turn keeps a single "view run" (`groupTurnReactions` read-time pairing; standalone while the reply is absent); `router_fallback` stays centered and unattributed.
7. **New-vs-continue reaction (D8)**: a `turn_started` reaction renders "Starting a new task" or "Continuing the earlier task" from the durable `turn_mode`, naming the execution session (falling back to the trigger body when untitled, and to the single line when no name resolves); `turn_dispatched` stays the neutral "Got it — queued"; `chat_dispatch` / `route_intent_session` report `opened_new=false` for a reuse and `true` only for a fresh create (locked by the builder unit test and the dispatch unit test).
8. **Continuation echo (D9)**: in an execution session started from a chat, a turn the user composes locally in that session (including the continue-after-stop case) posts its final output back to that chat as a standalone `agent_message` (`exec:{message_id}` idempotent, `sender_session_id` drillable, broadcast); chat-routed turns still write back through request/response with no double-write; `chat-append` accepts `agent_message` and still rejects `user_message` and unknown kinds.
9. **Intermediate state is not persisted**: after a fresh turn (1:1 / group @ / PM dispatch) reaches its terminal, the chat log contains no `turn_dispatched` / `turn_started` / `router_fallback` row; both pointer builders are gone and their old unit tests assert "nothing is written".
10. **Legacy rows are hidden**: a window carrying the three retired notices renders no text on either Desktop surface or Mobile, while genuine channel receipts (`budget_exhausted` / `delivery_failed` / `truncated` / `unavailable`) still render.
11. **Wait line**: it appears only for a turn that actually woke an agent — a `user_user` DM (no agent participant) shows nothing on open and nothing while a send is in flight; an un-@'d group message shows nothing; 1:1, a group @ (one broadcast row + `meta.mentions`) and a pinned execution turn all show it. Inside the send window (`sending=true`, in a chat that has an agent) the generic line shows even on an empty window; while the newest turn-opening human row has no terminal answer it shows `{{name}} is working on it…`; it disappears once a terminal lands, a card opens, or a newer **turn-opening** human row appears; an un-@'d aside landing after an in-flight turn keeps the line up; it is suppressed when a locate parked the window mid-history (`lastPos < total - 1`).
12. **Centered terminals**: an empty-body `aborted` / `failed` / `timeout` / `waiting` paints as a centered status line (`aborted` not red, `failed` / `timeout` red) with the "view run" drill and never as an agent bubble; a terminal with a body is still an ordinary bubble.
13. **Local stop**: stopping a chat-bound execution session's local turn leaves one `exec:`-idempotent empty `aborted` row in that chat; repeated stops do not duplicate it.
14. **Routing reaction row (D11)**: every routed turn that owes its chat a write-back (1:1 / group @ / PM dispatch / the router-off human turn / the degraded fresh create) leaves one `tr:{request_id}` `turn_routed` row after successful delivery, with `in_reply_to` / `agent_session_id` / `turn_mode` in meta and an empty body; a redelivered envelope adds no second row; all three surfaces render it as an agent avatar + name + bubble ("Starting a new task: X" / "Continuing the earlier task: X"), never centered; the wait line continues after it until the terminal.
15. **Avatar invariant (D11)**: the agent reply following an empty terminal row (a centered status line) wears its avatar + name again; the `turn_routed` reaction and the turn's real reply each wear their own header.
16. **Degraded create (with the ADR-099 revision)**: a chat-sourced human message the router degraded (`Fallback`) no longer reuses the intent_map's historical session — it goes through `chat_dispatch(Target::New)`, creating a fresh session bound to the same chat and re-pointing the mapping; the deterministic reuse for `PassThrough` (PM / agent-agent / response / router off) is unchanged.
17. **The execution view sends through the chat entry (D12)**: in a chat-bound execution session the composer's send goes to `/api/intents/chat-message` carrying `for_execution_session` and the client's `message_id`; chat shows one `user_message` written **as that user**, followed by the same session's terminal `agent_message` carrying an `in_reply_to` pointing at it, and the wait line disappears; the execution session's JSONL holds exactly one user row with that `message_id`; with no binding, or with no account, the send still goes to `POST /sessions/{sid}/messages` and chat gains no row; when the pin names a session that is not loaded the message is still delivered (through the ordinary route); a pinned turn's slash skill and `attached_items` take effect, and the chat row shows display names only — never a path or a documentId.
18. **The four failure faces D12 had to close (fix round)**: ① a pinned send whose bound chat is a group returns 200 and files its head in that group with `to` = the `pinned_agent` named instance, naming an instance that is not a participant of the chat returns 403 and writes no row, and an unpinned group send still returns 400; ② a pin naming a loaded session that is **bound to a different chat** does not run inside that foreign task — the turn falls back to the ordinary route in the sender's own chat; ③ when the turn ends in an agent-loop error or an unreadable attachment, chat still gets a `status=failed` terminal row pointing at that head row, so the wait line never hangs forever; ④ once the terminal row is durable, the mailbox's `user_message` request reads answered — `GET /api/intents/{message_id}` reports `answered=true` — and the sweeper never files a `fallback-` receipt for it.

## Compatibility and Migration

- No history migration: existing `turn_started` rows remain valid, their meaning narrowed to "round started", rendering alongside the new `turn_dispatched` rows.
- Zero data-side change for PM dispatch: its early pointer is exactly the `route_intent_legacy` write being renamed to `turn_dispatched`.
- Event-row text uses fixed i18n keys (`chatView.notice.turnDispatched` / `chatView.notice.turnStarted`); the body stores a human-readable short string, the meta stores `agent_session_id` for the drill, consistent with the existing pointer. D7 changes only these two keys' values (to agent voice) and the render attribution; the keys and the pointer contract are unchanged. D8 adds, on top of this, the `turn_mode` meta field and the two keys `chatView.notice.turnStartedNew` / `chatView.notice.turnStartedContinue` (with `{{name}}` interpolation) — a `turn_started` reaction picks one of them by `turn_mode` when a task name resolves, else falls back to `chatView.notice.turnStarted`; the `turn_dispatched` contract is unchanged.
- D9 widens the write-back basis without changing existing contracts: the chat-routed request/response write-back is unchanged; what is added is one more write-back source ("a chat-bound session's local turns") and one `chat-append` kind. Historical `aborted` rows are unchanged; a "continuation lost" that happened before the fix is not backfilled (those turns never had a chat row).
- The execute session view (including its read-only pending-queue mirror and todo progress) is kept; this change only alters the chat-side presentation.

**Rev. 2 (D10):**

- **No history migration**: legacy `turn_dispatched` / `turn_started` / `router_fallback` rows stay in their files, neither deleted nor rewritten, and are hidden at render time; the `turn_mode` field (D8) stays deserializable and is never produced again. Historical unread counts are not retroactively corrected.
- **The wait line needs no migration**: it is derived entirely from durable rows — a refresh re-derives the same line while the newest human message still has no terminal answer, and it vanishes once a terminal exists.
- **Old receipts still render**: genuine channel receipts such as `budget_exhausted` / `delivery_failed` / `truncated` / `unavailable` are unaffected.

**Rev. 3 (D11):**

- **One new row kind only, no legacy migration**: `turn_routed` is the sole reaction row written from Rev. 3 on; the `turn_dispatched` / `turn_started` / `router_fallback` rows hidden by Rev. 2 stay hidden — never backfilled, never revived. A pre-Rev.2 `turn_started` row carrying `turn_mode` still goes down the `RETIRED_NOTICES` hiding path; it is not mapped onto the new bubble.
- **The write whitelist is unchanged**: `chat-append` has accepted `system_notice` since Rev. 1, and `turn_routed` reuses that kind — no Gateway change.
- **The wording stays out of durable data**: the five locales gain `chatView.notice.turnRoutedNew` / `turnRoutedContinue` (with `{{task}}` interpolation); Mobile has no i18n layer and hardcodes the same Chinese copy per its existing convention.
- **The degraded-create semantics live on the ADR-099 side**: a `Fallback` for a chat-sourced human message now creates a fresh session (see the ADR-099 revision); this ADR only fixes that both paths (the router drain and the legacy degraded route) write the reaction through the same `turn_routed_meta`.

**Rev. 4 (D12):**

- **No existing row shape changes**: the fields and kinds of `user_message` / `agent_message` are untouched — a pinned turn only adds one more source for the head row (the execution composer) and one more `in_reply_to` on the terminal. No history migration is needed; an old execution session neither gains nor loses a row on upgrade.
- **`for_execution_session` is optional**: a `chat-message` request without it behaves exactly as before (that is the path chat's own composer takes), so Gateway, Runtime and the clients can be released in any order — there is no version lock.
- **`meta.exec_attachments` is a new meta key**: a reader that does not know it simply ignores it; the worst case is a chat row that does not show what was attached, never a parse or render failure.
- **No binding, no change**: an execution session with no chat binding, and local mode (no account), still take `POST /sessions/{sid}/messages` — that chain is byte-for-byte what it was before this revision.

## Non-Goals

- Do not reintroduce any form of execution live-state mirror on the chat side.
- Do not change the card-answer closed loop, or the @ fanout authorization and write-back channels.
- Do not change the semantics of the PM dispatch endpoint `POST /api/intents/task-dispatch`.
- Rev. 2 does not backfill any "was running at the time" compensation row into history; an unanswered human message already says that much.
- Rev. 3 restores no **progress** row (dispatch / round-open / the fallback receipt stay unpersisted and hidden); `turn_routed` answers only "which task did this message go to" — it is not an execution-status mirror and never updates with progress.
- Rev. 4 does not move attachment bytes across systems: the chat row carries display names only, never a reference the chat side could not open (both because of the ADR-009 §5 red line and because an unopenable reference is worse than none).
- Rev. 4 does not touch chat's own composer: it still sends plain chat messages, carries no `for_execution_session`, and routes exactly as before.
- Rev. 4 does not synchronize history between chat and the execution session: only the head of this turn moves from the execution surface into chat — nothing is copied back, mirrored, or re-read on the way.
